# Предметная модель Stageby

Источники: продуктовое описание `contracts/context/Система управления этапами строительства.md`,
Excel `contracts/context/ГПР Купидом 18.09.2026.xlsx` (лист «Окна») и уточнения заказчика.

## Подтверждённые сущности

| Сущность | Назначение и связи |
| --- | --- |
| Пользователь (`User`) | Сотрудник или исполнитель с ролью |
| Проект (`Project`) | Один объект строительства; содержит восемь этапов |
| Этап (`Stage`) | Один проект, один ответственный мастер, не более одного чек-листа |
| Чек-лист (`Checklist`) | Принадлежит этапу; содержит несколько пунктов |

Собственник хранится в карточке проекта. Клиентский доступ и пользователи-поставщики — будущие версии.
Пункт — вложенная часть чек-листа в API. Физическое хранение пунктов (таблица или структурированное поле)
определяется при проектировании БД. Четыре предметные сущности не запрещают вспомогательные таблицы для пунктов и сессий.

## Роли

| Роль | Код | Доступ |
| --- | --- | --- |
| Руководитель/прораб | `manager` | Все объекты, назначения, аналитика и финансы |
| Инженер-сметчик | `estimator` | Сметы, этапы и заявки, контроль закупки |
| Мастер участка | `foreman` | Только свой этап, материалы, инструмент, чек-лист и статусы |
| Приёмщик | `inspector` | Свои проверки, акт готовности и замечания |

Ответственный мастер и назначенный приёмщик — разные функции. В контракте предусмотрен `inspectorId`
для назначения приёмщика. Это решение проектирования для реализации доступа к своим проверкам.
Имя исполнителя из Excel не является уникальным логином. Учётные записи создаёт руководитель,
вход — по логину и паролю. Публичной регистрации нет. Первого руководителя нужно создавать
при развёртывании вне публичного API; соответствующая административная команда пока не реализована.

## Поля проекта

| Данные | Поле | Источник |
| --- | --- | --- |
| Название объекта | `title` | Название для отображения в приложении |
| Имя клиента/собственника | `ownerName` | Excel B2 и продуктовое описание |
| Адрес | `address` | Продуктовое описание |
| Широта и долгота | `coordinates` | Продуктовое описание; ссылка на карту формируется интерфейсом |
| Кадастровый номер | `cadastralNumber` | Excel C2; строка, может отсутствовать |
| Срок сдачи | `dueDate` | Excel D2; календарная дата без времени |
| Вариант дома | `houseDesign` | Excel F2, например «Семья 67» |
| Реквизит «договор» | `contractLabel` | Excel E2; исходный текст, смысл не уточнён |

«Проект» в колонке F означает вариант дома, а не всю сущность проекта.
Новый документ не объясняет значения «Мир» и «Штро А С» в колонке «договор».
Пока их можно сохранить текстом; нельзя автоматически считать номером договора или ID пользователя.
Порядковый номер Excel A2 не заменяет стабильный ID. Для новых сущностей ID — положительное целое число
`int32` (1–2147483647), назначаемое БД через автоинкремент и передаваемое в JSON как число.
Связанные идентификаторы, включая элементы массивов, имеют тот же тип. Системе также нужны `createdAt` и `updatedAt`.

## Этапы

Состав и названия одинаковы для всех проектов и не редактируются:

| Код | Название |
| --- | --- |
| `foundation` | Фундамент |
| `walls` | Стены |
| `roof` | Крыша |
| `windows` | Окна |
| `facade` | Фасад |
| `electrical` | Электрика |
| `plaster` | Штукатурка |
| `heating` | Отопление |

Подтипы работ могут отличаться: `workSubtypes` содержит список названий.
Плановые даты начала и окончания хранятся отдельно; фактические даты нельзя подменять плановыми.
Мастер назначается руководителем вручную, автораспределения нет.

Порядок отображения и зависимости — разные свойства. `position` задаёт фиксированный порядок типов,
`predecessorStageIds` для обязательных предшественников. Пустой список допускает параллельную работу.
Зависимости принадлежат одному проекту и не образуют циклов. Автоматического перепланирования нет.

## Статусы и приёмка

В описании: Создан → Назначен → Укомплектован → Старт → В работе → Приёмка → Выполнен → Выплачен.
Приёмщик может вернуть этап на доработку с замечаниями и сроком исправления.
В контракте дата исправления обязательна: интерфейс может предложить текущую дату + 2 календарных дня.
Приёмщик выбирает пункты для доработки. Сбрасываются только их отметки, остальные сохраняются.

В первой версии семь рабочих статусов, до «Выполнен» включительно. «Выплачен» отложен вместе
с платежами по бригадам: четыре суммы затрат не доказывают факт окончательного расчёта.
Общая карточка этапа не раскрывает финансы; суммы выдаются отдельными методами только руководителю.

## Чек-лист

Продуктовое описание предусматривает 3–4 контрольные точки с равным весом.
Прогресс рассчитывается по доле выполненных пунктов; для пустого чек-листа — 0.
Выполнение всех пунктов не заменяет приёмку и акт готовности.
Названия типовых пунктов не предоставлены: их нельзя выдумывать при создании проекта.
До настройки чек-лист может быть пустым.

По уточнению заказчика текущая версия полностью без фото. В контракте нет загрузки файлов
и требования фотоподтверждения. Для будущего модуля продуктовый документ задаёт хранение один год.
Выполнение пункта фиксирует пользователя и время на сервере. После старта состав чек-листа
не меняется. Завершение всех пунктов разрешает передать этап на приёмку, но не завершает его автоматически.

## План-факт и следующие модули

МАТ и СМР соответствуют затратам на материалы и работы. Продуктовое описание требует
отдельные план и факт — четыре показателя на этапе. Пустые ячейки не означают нулевые затраты.
Итоги вычисляются. Финансовые данные доступны руководителю.

Бригады и частичные выплаты требуют записей с получателем, суммой и датой;
одного флага «выплачено» недостаточно. По решению заказчика эти функции отложены.
Пока руководитель вручную вводит четыре суммы на этапе. Контракт использует целые копейки RUB:
`null` — сумма неизвестна, `0` — подтверждённый ноль. Итог проекта по показателю равен `null`,
если хотя бы на одном этапе этот показатель ещё не введён.

Материалы, поставщики, заявки, приёмка поставок, оборудование и выдача/возврат — следующие фазы.
ЭДО, клиентский доступ и нативное приложение в первую версию не входят.

Полноценные шаблоны проектов и прогнозы по неделям/месяцам описаны как требования,
но состав шаблонов и метод распределения затрат по времени не заданы.
Автосоздание восьми этапов не заменяет шаблон со сроками и контрольными точками.

## Особенности будущего импорта Excel

В файле 20 объектов. Блок объекта: реквизиты и исполнители, состояние работ, МАТ, СМР, разделитель.
Все ячейки затрат пустые. Отдельных пользователей и чек-листов нет.

- K29 и K34: 0.5 с форматом 0% означает 50%. Перенос числа не должен выдумывать выполненные пункты.
- H59: `21-31.09.2026` содержит несуществующую дату 31 сентября.
- I54: хранится 28 августа 2026 года; соседний этап стен указан на сентябрь. Нужна проверка значения.
- I24 и I39: интервалы пересекают месяцы, начальный месяц явно не указан.
- I59: `1-10 2026` неоднозначно без уточнения формата.
- Ячейки состояния смешивают даты, интервалы, проценты, «выполнен» и замечания.
- «Нет фото котельной» и «ПОДТОПЛЕНИЕ» — замечания, а не автоматически созданные пункты или статусы.
- Составные и похожие имена исполнителей нельзя автоматически разделять или объединять.

Исходные файлы сохраняются без изменений. Импорт — отдельная задача после согласования модели.

## Контракт и реализация

Источник HTTP-контракта — [stageby.yaml](../contracts/references/stageby/stageby.yaml),
описания сущностей лежат в соседних папках. Сценарии и правила приведены в
[руководстве API](api-contract.md). Собранная спецификация и типы API/Web генерируются.

В этом изменении подготовлен контракт. Новые серверные маршруты, схема БД, сессии и интерфейс
ещё не реализованы. Существующий модуль `todos` сохранён для совместимости демонстрационного приложения.
