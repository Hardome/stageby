# Согласованные правила edited.ver2

Источник — текущая редакция [ТЗ edited.ver2](../rules/ТЗ%20на%20разработку%20страницы%20и%20сценарии%20edited.ver2.md)
и согласованные ответы, зафиксированные ниже.
Редакция решений от 12.10.2026 описана в [предметной модели](../rules/domain-model.md) и
[API-документации](../rules/api-contract.md). Результаты проверки серверной реализации,
OpenAPI и БД описаны в [заметке о доработках бэкенда](../reports/edited-ver2-backend-update-release.md).
[Заметка о выпуске](../reports/edited-ver2-release.md) сохраняется как история предыдущей поставки.

| Решение | Правило |
| --- | --- |
| R1 | Ручные планы работ и материалов хранятся на этапе. Выплаты принадлежат этапу и фиксируют текущего активного мастера при создании; получатель не меняется. Сводка к дате использует планы этапов с окончанием не позже даты и оплаты тех же этапов не позже даты; остаток сохраняет переплату. |
| R2 | Панель содержит таблицу и индикаторы. Счета принадлежат этапу; заявки на материалы оформляются вне системы. |
| R3 | Сохранено и дополнено: строка панели показывает первый включённый по позиции этап, который ещё не paid. Исключённые этапы не выбираются; строки без даты начала идут в конце и не имеют предупреждения о неназначенном мастере за 7 дней. |
| R4 | Сохранено и дополнено: объект завершён, когда все включённые этапы paid. Дополнительный этап участвует в завершении; его добавление к завершённому объекту возвращает объект в активные. Исключённые этапы не учитываются в завершении и активном счётчике. |
| R5 | Невыполненный предшественник вызывает предупреждение, но не блокирует старт. |
| R6 | Материалы: красный при отсутствии счетов или открытой нехватке; жёлтый при неполной оплате/доставке; зелёный при полной оплате и доставке без нехватки. Подписи частичной оплаты и доставки независимы. |
| R7 | Нехватку отдельно закрывает руководитель. |
| R8 | Фото сохраняются при выходе; выполнение подтверждается отдельным действием «Готово». |
| R9 | Вход по логину и паролю; телефон необязателен. |
| R10 | Заменено: создание на отдельной странице в той же вкладке с двумя шагами «Объект» и «Этапы»; сохранить можно с первого шага или любого экрана этапа. Неоткрытые стандартные этапы форма передаёт включёнными, с шаблонами и без дат, мастера и планов. После успеха переход на дашборд, а не на объект. Повтор не создаёт дубль. |
| R11 | После приёмки статус автоматически равен paid при заданном плане работ и сумме выплат ≥ плана, иначе completed. Правки плана и выплат пересчитывают статус в обе стороны; фактические даты сохраняются. Нулевой план считается погашенным, null — незаданным. |
| R12 | Ручные планы работ и материалов хранятся на этапе. Выплаты принадлежат этапу и фиксируют текущего активного мастера при создании; получатель не меняется. Сводка к дате использует планы этапов с окончанием не позже даты и оплаты тех же этапов не позже даты; остаток сохраняет переплату. |
| R13 | Наличные выплаты вносит руководитель без документов напрямую на этап. Получатель фиксируется по текущему активному назначению и не меняется; переназначение влияет только на новые выплаты. Назначенный мастер читает собственные выплаты и общие итоги этапа; снятие назначения отзывает доступ. |
| R14 | Дополнено: даты этапа независимо nullable, их можно задавать, менять и очищать отдельно. Каждая заданная дата проверяется относительно обеих границ проекта; порядок — только при наличии обеих. Пересечения разрешены, соседние этапы не переносятся. Даты после старта можно менять, фактические даты сохраняются. Дата выплаты не ограничивается сроками проекта. |
| R15 | Счета добавляются после создания объекта в существующий этап. |
| R16 | Удаление фото по сроку хранения сохраняет выполнение, прогресс и статус. Новое выполнение и доработка требуют нового фото. |
| R17 | Серверный календарь — Екатеринбург UTC+5; диапазон панели — сегодня…+30 дней включительно. Адаптивность и браузерные проверки выполняются по планам экранов. |
| R18 | Приёмка подтверждается руководителем без файла акта. |

Решения R2, R5–R9 и R15–R18 сохранены. R3, R4, R11, R13 и R14 дополнены;
R1, R10 и R12 заменяют прежние формулировки. Сохраняющиеся правила фото, приёмки, лимитов
файлов и счетов, входа и независимой доставки не отменяются финансовыми изменениями.

## Заменённые правила предыдущей реализации

Эта таблица сохраняет прежние правила для сравнения, но они больше не определяют целевое поведение.

| Область | Прежнее правило | Целевое правило |
| --- | --- | --- |
| Планы этапа и объекта | Предложено убрать план работ этапа и вычислять его из строк | Уточнение пользователя от 12.10.2026 заменяет это предложение: `plannedWorkAmountMinor` и `plannedMaterialAmountMinor` — хранимые nullable-поля этапа, руководитель задаёт и редактирует их вручную. Общие планы объекта вычисляются как суммы ручных планов включённых этапов, не редактируются и не хранятся в БД. Факты вычисляются из выплат и оплат счетов. |
| Получатель выплаты | Руководитель передаёт recipientId | Сервер фиксирует текущего активного назначенного мастера этапа. Получатель не меняется, прошлые выплаты сохраняются после переназначения. |
| История выплат для мастера | Историю читает только руководитель | Назначенный мастер читает свои выплаты; общие итоги этапа по всем получателям. |
| Выплаты без детализации плана | Строки и распределение сумм | Строки удалены; остаются ручной план этапа и фактические выплаты. |
| Финансовый периметр панели (R1/R12) | Работы и материалы отбираются только по окончанию этапа; факт не ограничен датой оплаты | Работы и материалы по окончанию этапа; факт только того же периметра и только с датой оплаты ≤ D. |
| Факт материалов (R12) | Сумма выставленного оплаченного счёта | Отдельная фактическая сумма оплаты и введённая календарная дата; при снятии оплаты обе очищаются, ручной план не меняется. |
| Даты этапа (R14) | Обе даты обязательны | Независимо nullable, проверка каждой по обеим границам проекта, порядка — только при обеих. |
| Правки завершённого этапа (R11) | PATCH не меняет completed/paid | Даты, мастер и планы редактируются после старта; статус completed/paid пересчитывается автоматически в обе стороны по плану и выплатам. |
| Правка чек-листа | Ограничение по текущему статусу created/assigned/supplied | Ограничение по `actualStartDate`: снятие выполнения не отменяет старт и не разрешает изменение состава. |
| Справочник | Восемь типов, у каждого активный шаблон | Восемь стандартных типов с шаблонами и девятый `additional` без шаблона, только при редактировании, с непустым индивидуальным чек-листом и последней позицией. |
| Редактирование объекта | PATCH реквизитов и отдельные операции этапов | Один атомарный запрос всей формы с проверкой версий проекта и затронутых ресурсов, итогового состояния и единым аудитом. Отдельные операции сохраняются с согласованными блокировками. |
| Включённость | Нет операции исключения и восстановления | До старта и без фото (включая удалённые), счетов и выплат этап можно исключить, сохранив планы и чек-лист; восстановление той же записи. Тип уникален и среди исключённых записей, минимум один этап включён. Пропуск этапа в PATCH не исключает его. |
| Завершение и дополнительный этап (R4) | Завершение после выплаты всех существующих этапов | Завершение по включённым этапам; новый дополнительный этап возвращает завершённый объект в активные. Исключённый additional восстанавливается вместо создания второго. |
| Переход после создания (R10) | На страницу объекта | На дашборд в той же вкладке. |

## Условия поставки и сохранения

Целевая установка — БД без прикладных данных. Перенос существующих объектов и выплат
не реализуется, заполненная БД не входит в поставку; автоматического удаления её данных нет.
Новые миграции не переписывают `0000_initial.sql`. Источники OpenAPI и generated-файлы
обновляются на следующих шагах, generated-файлы вручную не редактируются.

Создание атомарно сохраняет объект, этапы, чек-листы, связи PDF и аудит;
повтор успешного запроса с тем же ключом идемпотентности не создаёт вложенных дублей.
Клиент, адрес, координаты и обе даты проекта обязательны; включён минимум один стандартный
этап без повторов, `additional` при создании запрещён. Неуказанный индивидуальный чек-лист
копируется из активного шаблона, переданный пустой список отклоняется. Счета — только после создания.

Редактирование загружает данные тех же двух шагов, включая исключённые этапы для руководителя,
чек-листы и версии. Сохранение атомарно, ошибка любой части отменяет всё. Отсутствующее поле
сохраняет значение, `null` очищает nullable-поле, включённость меняется явно.
Изменения включённости увеличивают версию проекта; проверяются версии затронутых вложенных
ресурсов. Совместные правки сроков проверяются по итоговому состоянию без отказа на промежуточном.
Архивные объекты не изменяются. Планы работ и материалов этапа задаёт вручную только руководитель;
общие планы объекта — вычисляемые суммы планов включённых этапов. Выплаты изменяются через
их ID и версии. Выплаты принадлежат этапу напрямую.

## Уточнение источника планов от 12.10.2026

План работ и план материалов этапа — ручные nullable-поля руководителя, сохраняемые в БД.
Общий план работ объекта = сумма ручных планов работ включённых этапов;
общий план материалов объекта = сумма ручных планов материалов включённых этапов.
Агрегаты объекта не редактируются и не хранятся в БД. Если план составляющего этапа неизвестен,
план соответствующей категории объекта и её остаток равны `null`, факт остаётся доступен.
Выплаты и счета меняют вычисляемые факты, а не ручные планы этапов.

Это уточнение заменяет прежнее предложение убрать поле плана работ этапа и считать его из строк.
Уточнение от 18.10.2026: строки плана удалены. Сводка к D использует ручные планы этапов
с окончанием не позже D и фактические выплаты тех же этапов с датой не позже D.
