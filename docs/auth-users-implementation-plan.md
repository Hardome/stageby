# План реализации миграций, авторизации и API пользователей

Статус: в работе. Этапы 1–4 завершены.

Цель — подготовить схему PostgreSQL, реализовать безопасную серверную авторизацию с хранилищем сессий и добавить API авторизации и управления пользователями в соответствии с существующим OpenAPI-контрактом.

## Исходное состояние

- OpenAPI-контракт валиден и уже описывает маршруты `auth` и `users`.
- API компилируется, но из прикладных модулей реализован только демонстрационный `todos`.
- В базе существует только таблица `todos`.
- Публичной регистрации нет: пользователей создаёт руководитель.
- Первый руководитель должен создаваться административной командой вне публичного HTTP API.
- Непрозрачный Bearer-токен действует не более 12 часов.

## Решения и риски

1. Текущий глобальный rate limit учитывает в основном IP. Для login требуется отдельное ограничение по комбинации IP и нормализованного login.
2. Встроенный Argon2 появился не во всех релизах Node.js 24. До реализации нужно выбрать между повышением минимальной версии Node.js и отдельной поддерживаемой библиотекой Argon2id.
3. OpenAPI возвращает Bearer-токен в теле ответа. Для браузерного клиента отдельно нужно определить безопасный способ хранения: токен не следует помещать в `localStorage` или `sessionStorage`.
4. Проверка `user_in_use` требует таблиц этапов и назначений уже в текущем инкременте.
5. Изменение роли, активности или пароля и отзыв сессий должны быть одной атомарной операцией.

## Оценка

Ориентировочная длительность — 8–10 рабочих дней одного backend-разработчика:

- модель БД и миграции: 2–3 дня;
- пароли, токены и хранилище сессий: 1–2 дня;
- auth plugin и Auth API: 1–2 дня;
- Users API и транзакционные ограничения: 2 дня;
- административная команда, тесты и документация: 1–2 дня.

Оценка уточняется после фиксации физической модели всех доменных таблиц и выбора реализации Argon2id.
