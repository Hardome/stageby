# Разработка web-фич Stageby

Правила ниже относятся к `web/`. Нумерация сохраняет согласованный перечень; пункт 23 исключён. Примеры показывают код Stageby. Если подходящего работающего примера ещё нет, это указано отдельно: пример нельзя заменять вымышленным кодом.

## Карта проекта

```text
web/src/
├── app/        # запуск, провайдеры, маршруты, общие layout
├── pages/      # сборка экранов и связь с URL
├── widgets/    # крупные блоки, используемые разными страницами
├── features/   # действия и сценарии пользователя
├── entities/   # добавлять при повторном использовании предметного объекта
├── shared/     # инфраструктура, независимые UI-компоненты и утилиты
└── generated/  # результат генерации; вручную не редактировать
```

Рабочая цепочка раздела пользователей: [маршрут](../../web/src/app/routes/_auth/users/index.tsx) → [страница](../../web/src/pages/users/users.page.tsx) → [публичный API фичи](../../web/src/features/users/index.ts) → [список](../../web/src/features/users/ui/list/users-list.tsx). Порядок разработки новой фичи: определить пользовательский сценарий и контракт, выбрать слой, добавить маршрут и страницу при необходимости, реализовать действие в фиче, покрыть состояния и тесты, затем запустить проверки.

## Структура и границы

1. **Выбирайте слой по ответственности.** `app` связывает приложение, `pages` собирает экран, `widgets` объединяет крупные повторяемые блоки, `features` реализует действия, `entities` хранит повторно используемый предметный объект, `shared` не зависит от предметной области. Это снижает сцепление между сценариями. Например, [главная страница](../../web/src/pages/home/home.page.tsx) собирает экран из фичи списка задач и общих UI-компонентов.

2. **Держите декларации маршрутов в `app/routes`.** Маршрут подключает компонент страницы и задаёт проверку параметров; основную разметку держите в `pages`. Так URL-структура остаётся видимой отдельно от интерфейса. Пример: [маршрут пользователей](../../web/src/app/routes/_auth/users.tsx) и [страница списка](../../web/src/pages/users/users.page.tsx).

3. **Связывайте URL и экран на уровне страницы.** Страница читает search-параметры и передаёт фиче данные и обработчики. Компонент фичи сообщает о выборе фильтра или страницы, а не управляет маршрутом списка самостоятельно. Это позволяет использовать фичу в другом окружении. Пример: [обработчики `UsersPage`](../../web/src/pages/users/users.page.tsx) и [свойства `UsersList`](../../web/src/features/users/ui/list/users-list.tsx).

4. **Создавайте `entities` при реальном повторном использовании предметного объекта.** Не переносите туда код ради заполнения слоя. Сейчас роли и данные форм относятся к одному разделу и лежат в [модели фичи пользователей](../../web/src/features/users/model/data.ts); перенос понадобится, когда эти правила будут нужны нескольким независимым фичам.

5. **Открывайте срез через `index.ts`.** Страница импортирует поддерживаемые экспорты среза, а внутренние файлы остаются свободны для рефакторинга. Пример: [публичный API пользователей](../../web/src/features/users/index.ts) и его [использование страницей](../../web/src/pages/users/users.page.tsx).

6. **Используйте алиасы `@…` и сохраняйте границы срезов.** Для кода проекта используйте `@pages`, `@features`, `@entities`, `@shared`, `@api` и остальные настроенные алиасы; для тестовых помощников — `@tests`. Относительные импорты допустимы только внутри одного модуля и не глубже `../../`. Из соседнего среза используйте только публичный `index.ts`, не его внутренние файлы. Исключение для связей сущностей — адресный публичный API `@x`. Пакеты импортируйте по их npm-именам. Пример: [поля редактора](../../web/src/features/projects/edit/ui/edit-project-fields.tsx) используют [публичный API объекта](../../web/src/entities/project/index.ts).

7. **Раскладывайте файлы внутри среза по назначению.** `ui` содержит компоненты и разметку, `model` — данные и общие типы, `lib` — схемы, преобразования и хуки. Выносите в `lib` сложную логику формы: черновики, согласование версий, перезагрузку с сохранением правок и несколько связанных действий. Простую настройку формы, мутацию и короткие обработчики можно оставлять рядом с разметкой; отдельный хук не нужен для каждой формы. Интерфейс пропсов, используемый только одним компонентом, оставляйте рядом с ним; общий тип размещайте в `model`. `api` добавляйте для ручной интеграции, если её нет в сгенерированном клиенте. Не создавайте пустые каталоги. Пример: [модель редактора](../../web/src/features/projects/edit/model/types.ts), [хук формы](../../web/src/features/projects/edit/lib/use-project-edit-form.ts), [компонент формы](../../web/src/features/projects/edit/ui/edit-project-form.tsx).

8. **Каждый компонент размещайте в отдельном файле, кроме компонентов `shared/ui`.** Правило относится и к небольшим неэкспортируемым компонентам: формы, поля, кнопки, состояния и диалоги должны иметь собственные файлы внутри своего среза. Только в `shared/ui` связанные компоненты одного семейства можно держать вместе. Например, [семейство компонентов карточки](../../web/src/shared/ui/card.tsx) остаётся одним модулем, а [форма редактора](../../web/src/features/projects/edit/ui/edit-project-form.tsx) собирает отдельные [поля](../../web/src/features/projects/edit/ui/edit-project-fields.tsx), [действия](../../web/src/features/projects/edit/ui/edit-actions.tsx), [сообщения](../../web/src/features/projects/edit/ui/edit-project-feedback.tsx) и [диалог](../../web/src/features/projects/edit/ui/reset-project-dialog.tsx).

9. **Соблюдайте именование.** Файлы — `kebab-case`, компоненты и типы — `PascalCase`, функции и переменные — `camelCase`. Название должно отражать действие или содержимое. Примеры: [файл `user-search.ts`](../../web/src/features/users/lib/user-search.ts), тип `UsersSearch` в [модели](../../web/src/features/users/model/types.ts), компонент `UsersList` в [списке](../../web/src/features/users/ui/list/users-list.tsx).

10. **Перед добавлением файла проверяйте путь по цепочке маршрута.** Сначала решите, это экран, действие, повторяемый блок или общая утилита; затем выбирайте каталог из карты выше. Для примера проследите [маршрут](../../web/src/app/routes/_auth/users/index.tsx), [страницу](../../web/src/pages/users/users.page.tsx), [фичу](../../web/src/features/users/index.ts) и [общий компонент поля](../../web/src/shared/ui/field.tsx).

## Маршруты и данные

11. **Проверяйте параметры URL до запроса.** Search-параметры разбираются [схемой раздела](../../web/src/features/users/lib/schemas.ts) через [функцию разбора](../../web/src/features/users/lib/user-search.ts); динамический `userId` проверяется до включения запроса в [редакторе пользователя](../../web/src/features/users/ui/user-editor.tsx). Некорректный ввод не должен отправлять запрос с неверным ID.

12. **Храните состояние списка в URL.** Фильтры и смещение должны переживать обновление страницы и обратную навигацию. При смене фильтра сбрасывайте смещение; при перелистывании меняйте только его. Пример: [обработчики страницы пользователей](../../web/src/pages/users/users.page.tsx).

13. **Преобразовывайте параметры URL в параметры API в одном месте.** Укажите размер страницы и значения по умолчанию, уберите пустой поиск, сохраните `false` как действующий фильтр. Пример: [`getUsersQuery`](../../web/src/features/users/lib/user-search.ts) и [его тест](../../web/src/features/users/lib/user-form.test.ts).

Например, [страница пользователей](../../web/src/pages/users/users.page.tsx) сбрасывает смещение при смене фильтра, а [`getUsersQuery`](../../web/src/features/users/lib/user-search.ts) задаёт размер страницы перед запросом:

```tsx
search: (previous) => ({ ...previous, ...values, offset: 0 }),
```

```ts
limit: 20,
offset: search.offset ?? 0,
isActive: search.isActive,
```

14. **Показывайте разные состояния запроса.** Первую загрузку, ошибку с повтором, пустой результат и данные нельзя смешивать в один экран. Пользователь должен понимать, что произошло и что делать дальше. Пример: [список пользователей](../../web/src/features/users/ui/list/users-list.tsx) и [ошибка с повтором](../../web/src/features/users/ui/user-error.tsx).

15. **Обозначайте фоновое обновление списка.** При повторном запросе показывайте статус, помечайте занятость секции и не допускайте повторного перелистывания до ответа. Пример: [статус и пагинация списка](../../web/src/features/users/ui/list/users-list.tsx).

16. **Используйте сгенерированный клиент и контрактные типы.** Исходник API-контракта находится в `contracts/references/`; после изменения контракта запускайте генерацию. Код в `web/src/generated/` не редактируйте вручную. Пример использования сгенерированных типов и хуков: [список пользователей](../../web/src/features/users/ui/list/users-list.tsx); конфигурация генерации — [kubb.config.ts](../../web/kubb.config.ts).

17. **После мутации согласуйте кэш с сервером.** Обновите конкретную запись, инвалидируйте затронутые списки и только затем завершите сценарий навигацией и сообщением. Пример: [`useUserActions`](../../web/src/features/users/lib/use-user-actions.ts).

18. **Не раскрывайте причину недоступности страницы или аккаунта.** Запрещённая ролью страница, недоступный ресурс, ответ `403`/`404` при загрузке страницы и неизвестный адрес показывают одну нейтральную заглушку «404 — Страница не найдена» без указания недостатка прав или существования ресурса. При `403` обновляйте сведения о пользователе. При `401` очищайте клиентскую сессию и защищённый кэш, затем отправляйте на вход с безопасным адресом возврата. Фронтенд не различает отсутствующую/истёкшую сессию и отключённый аккаунт: отдельное сообщение о блокировке не показывается. При входе неверные реквизиты и отключённый аккаунт дают одно сообщение «Неверный логин или пароль.». Руководитель (`manager`, администратор) может просматривать все защищённые страницы, включая страницы мастера; отдельной роли администратора нет. Видимость ссылки и клиентская проверка роли дополняют серверную проверку прав. Примеры: [общая заглушка](../../web/src/shared/ui/not-found.tsx), [обработка сессии](../../web/src/shared/context/auth/lib/use-auth-session.ts), [страница мастера](../../web/src/app/routes/_auth/my-stages.tsx).

## Формы и UI

19. **Стройте схему формы на контрактной схеме.** Добавляйте правила интерфейса — подтверждение пароля, нормализацию необязательного поля — без дублирования API-ограничений. Пример: [схемы форм пользователей](../../web/src/features/users/lib/schemas.ts) и [их тесты](../../web/src/features/users/lib/user-form.test.ts).

20. **Связывайте поле, подпись и ошибку.** У поля должны совпадать `id` и `htmlFor`; при ошибке выставляйте `aria-invalid` и ссылайтесь на текст через `aria-describedby`. Пример: [текстовое поле формы](../../web/src/features/users/ui/form/text-field.tsx) и [поле роли](../../web/src/features/users/ui/form/profile-fields.tsx).

Короткий фрагмент из [текстового поля](../../web/src/features/users/ui/form/text-field.tsx):

```tsx
<FieldLabel htmlFor={properties.id}>{label}</FieldLabel>
<Input
  {...properties}
  className="min-h-11"
  aria-invalid={Boolean(error)}
  aria-describedby={error ? `${properties.id}-error` : undefined}
/>
{error && <FieldError id={`${properties.id}-error`}>{error}</FieldError>}
```

21. **Управляйте отправкой явно.** Блокируйте повторный submit во время запроса, показывайте состояние ожидания, после успеха завершайте сценарий, после ошибки сохраняйте ввод и объясняйте проблему. Пример: [создание пользователя](../../web/src/features/users/ui/form/create-user-form.tsx), [кнопки формы](../../web/src/features/users/ui/form/form-actions.tsx), [тест формы создания](../../web/src/features/users/ui/form/create-user-form.test.tsx).

22. **Добавляйте черновик только при понятной потребности.** Проверяйте прочитанные данные схемой, отделяйте черновики пользователей, очищайте их при успешном действии и выходе из сессии. Пароль не сохраняйте. Пример: [черновик создания](../../web/src/features/users/lib/create-draft.ts), [общее хранилище](../../web/src/shared/lib/storage/session-drafts.ts), [тест жизненного цикла](../../web/src/features/users/ui/form/create-user-form.test.tsx).

24. **Повторяйте код на правильном уровне.** Предметные состояния и действия оставляйте внутри фичи; в `shared` выносите только элементы, которым не нужны знания о пользователях, задачах и других областях. Пример: [ошибка пользователя](../../web/src/features/users/ui/user-error.tsx) использует [общую кнопку](../../web/src/shared/ui/button.tsx) и [общее пустое состояние](../../web/src/shared/ui/empty.tsx).

## Стиль и проверка

25. **Следуйте конфигурации форматирования.** Два пробела, LF, одинарные кавычки в TS/JS и точки с запятой задаются [biome.json](../../web/biome.json). Ручные исключения не добавляйте ради одного файла; пример отформатированного компонента — [поиск пользователей](../../web/src/features/users/ui/list/search-input.tsx).

26. **Разделяйте проверку и исправление файлов.** Для чтения результата используйте команды без `--fix` и `--write`: `corepack pnpm exec biome check .`, `corepack pnpm exec eslint . --max-warnings=0`, `corepack pnpm exec stylelint "src/**/*.css" --allow-empty-input`. Скрипты `lint:*` в [package.json](../../web/package.json) могут переписать файлы — применяйте их осознанно.

27. **Тестируйте нетривиальные преобразования возле реализации.** Проверяйте нормальный и ошибочный ввод там, где ошибка повлияет на запрос, навигацию или сохранённые данные. Простые обёртки не требуют отдельного теста. Пример: [тест схем и поиска](../../web/src/features/users/lib/user-form.test.ts) рядом с [преобразованием параметров](../../web/src/features/users/lib/user-search.ts); [тест черновика](../../web/src/features/users/lib/create-draft.test.ts).

28. **Проверяйте значимый пользовательский риск, а не каждый компонент.** Добавляйте сценарный тест, если меняется поведение, которое трудно проверить чистой функцией: переходы по списку, работа кэша, отзыв сессии. Не дублируйте одинаковый путь тестом каждого слоя.

29. **Перед завершением запускайте набор проверок.** Из `web/`: `corepack pnpm exec biome check .`, `corepack pnpm exec eslint . --max-warnings=0`, `corepack pnpm exec stylelint "src/**/*.css" --allow-empty-input`, `corepack pnpm exec steiger ./src`, `corepack pnpm exec tsc -b --pretty false`, `corepack pnpm exec vitest run`, `corepack pnpm exec vite build`. Фиксируйте результаты в описании изменения; состав инструментов указан в [package.json](../../web/package.json).

30. **Подкрепляйте действующее правило работающим примером.** В тексте правила укажите причину, ожидаемое поведение и ссылку на исправленный файл Stageby. Образец такого описания — пункт 12 и [реальный обработчик URL](../../web/src/pages/users/users.page.tsx).

31. **Отделяйте идеи на будущее от действующих правил.** Пока в Stageby нет реализации, помечайте идею как предложение и не подставляйте вымышленный пример. Текущая карта проекта выше показывает `entities` как условный слой; [модель пользователей](../../web/src/features/users/model/data.ts) остаётся в фиче до появления повторного использования.

32. **Описывайте несколько или сложные пропсы отдельным интерфейсом.** Для двух и более собственных пропсов, callback, составного типа или предметного объекта объявляйте локальный `interface <Component>Properties` рядом с компонентом. Готовый тип атрибутов наследуйте, если компонент дополняет его. Интерфейс экспортируйте только при использовании вне файла. Один простой скалярный пропс можно оставить прямо в сигнатуре. Примеры: [несколько пропсов списка](../../web/src/features/users/ui/list/users-list.tsx), [наследование свойств поля](../../web/src/features/users/ui/form/text-field.tsx), [один простой пропс](../../web/src/features/users/ui/form/profile-fields.tsx).

33. **Все импорты размещайте в начале файла.** После комментариев и директив идут импорты, затем типы, константы и реализация. Импортов после объявлений, функций и компонентов быть не должно. Это проверяет правило Biome `nursery/useImportsFirst` в установленной версии 2.5.14. Пример: [навигация формы](../../web/src/entities/project/ui/project-progress.tsx).

34. **Ограничивайте файл 200 строками, ориентируйтесь на 150.** Считайте весь файл, включая импорты, комментарии и пустые строки. Правило относится также к хукам, утилитам, фикстурам и тестам; сгенерированные файлы не редактируйте вручную. Делите код по ответственности, а тесты — по сценариям с общей подготовкой. Связанные семейства UI-примитивов, например [combobox](../../web/src/shared/ui/combobox.tsx), могут превышать ориентир: не дробите их механически ради числа строк. Не сокращайте имена, не уплотняйте разметку и не убирайте полезные отступы ради лимита. Пример разделения по ответственности: [чек-лист](../../web/src/entities/project/ui/stage-checklist.tsx) и [его пункт](../../web/src/entities/project/ui/stage-checklist-item.tsx).

35. **Проверяйте читаемость всего diff перед завершением.** Каждый компонент должен иметь свой файл с исключением для `shared/ui` по пункту 8, импорты — стоять в начале, файлы — соблюдать правило размера с его исключениями, сложная логика — находиться в соответствующем сегменте. Успешные линтеры и тесты не заменяют эту проверку. Сначала исправьте нарушения, затем сообщайте о готовности изменения.

36. **Разделяйте логические блоки пустой строкой.** Отделяйте настройку формы, группы состояния, вычисляемые значения, каждый эффект и обработчики друг от друга. Перед `return` после других действий ставьте пустую строку. В тестах разделяйте подготовку, действие и проверку результата; следующий сценарный шаг начинайте с новой группы. Связанные объявления одного блока оставляйте вместе. Не делайте код плотнее ради лимита строк. Пример: [хук редактора](../../web/src/features/projects/edit/lib/use-project-edit-form.ts) и [ограничения исключения](../../web/src/features/projects/edit/lib/project-exclusion-reasons.ts).

37. **До изменения сравните соседние реализации.** Прочитайте ближайшие файлы с той же ответственностью и соблюдайте их расположение импортов, логические отступы, имена и разделение `model/lib/ui`. Не копируйте замеченные нарушения: ориентируйтесь на действующие правила и читаемые примеры. Для формы объекта сравните [форму пользователя](../../web/src/features/users/ui/form/create-user-form.tsx) и [соседние компоненты формы](../../web/src/features/users/ui/form/form-actions.tsx).

38. **Группируйте связанные фичи по предметной области.** Размещайте отдельные сценарии в `features/<область>/<действие>`, например `features/projects/create`, `edit`, `list`, `view`. Название области не повторяйте в имени дочерней папки. Каждая дочерняя фича сохраняет собственный публичный `index.ts` и сегменты `model/lib/ui` по назначению. Папка группы только объединяет фичи: не добавляйте в неё общий `index.ts` или бизнес-логику, не открывайте через неё внутренности соседних фич. Это делает сценарии одного раздела видимыми вместе и сохраняет границы срезов. Примеры: [создание](../../web/src/features/projects/create/index.ts), [редактирование](../../web/src/features/projects/edit/index.ts), [список](../../web/src/features/projects/list/index.ts) и [просмотр](../../web/src/features/projects/view/index.ts).

## Состояния загрузки

Составной скелетон из нескольких элементов выносите в отдельный компонент и файл рядом с компонентом, который он заменяет: `dashboard-projects-skeleton.tsx`, `dashboard-project-card-skeleton.tsx`. Это правило действует для всех экранов. Скелетон повторяет колонки, строки, отступы и адаптивные варианты исходного блока; статические заголовки и подписи остаются видимыми. Одиночный `Skeleton` допустим на месте одного динамического значения. Общий скелетон используйте только для блоков с действительно одинаковой структурой; не заменяйте им сложную таблицу или карточку другой формы.

Для загрузки серверных данных используйте визуальный `DataRegion` и правила раздела «Загрузка динамических данных» в [дизайн-системе](design-system.md). Передавайте штатные флаги запроса: `isLoading` для первой загрузки, `isFetching` для обновления. При смене параметров одного списка или расчёта задавайте `placeholderData: keepPreviousData`; флаги `isPlaceholderData && isFetching` включают блокирующий слой через `isRefreshing`. Данные и кэш остаются в TanStack Query, без дополнительного хранения ответов и сравнения параметров. Дату внутри сводки берите из показанного ответа сервера.

Фильтры и кнопка повтора находятся вне блокируемой области. Коррекцию страницы после удаления последнего элемента выполняйте только по завершённому ответу текущего запроса, а не по `placeholderData`. Фоновые запросы не размонтируют формы и сохраняют ввод; повторное перелистывание блокируется до ответа по правилу 15. Не включайте сохранение предыдущих данных глобально: при смене ID сущности нужен отдельный результат. Обработку ошибок, сессии и доступа оставляйте в соответствующих возможностях.

## Быстрый шаблон новой фичи

1. Опишите действие пользователя, его входные данные, результат и ошибки.
2. Найдите существующий публичный API и выберите слой по правилам 1–7.
3. При новом URL добавьте маршрут и страницу по правилам 2–3, 11–13.
4. Реализуйте состояния запроса и форму по правилам 14–22.
5. Добавьте сценарные тесты и выполните проверки по правилам 25–29.
6. Если новое решение требует нового общего правила, сначала согласуйте его, затем добавляйте сюда с примером из исправленного кода Stageby.
