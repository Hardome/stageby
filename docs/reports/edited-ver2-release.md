## Проверки

Vitest создаёт отдельную PostgreSQL, применяет начальную миграцию и удаляет тестовую БД.
Рабочая БД не очищается. `test/migrations.test.ts` отдельно проверяет чистую установку,
повторный запуск, внешние ключи, индексы, ограничения и восемь типов этапов с 34 пунктами.
`test/checklist-templates.test.ts` проверяет сохранность индивидуальных списков,
фотоподсказок и прогресса при повторном применении миграции.

## Изменения API для фронтенда

Актуальный источник — `contracts/openapi.yaml`, клиент обновляется codegen.

- Счета этапа: GET/POST `/stages/{stageId}/material-invoices`, PATCH `/material-invoices/{invoiceId}`.
- Нехватка создаётся POST `/material-invoices/{invoiceId}/shortages`; устранение —
  POST `/material-shortages/{shortageId}/resolution` только руководителем.
- Создание объекта требует `Idempotency-Key` и список включённых стандартных этапов.
  Для неоткрытого этапа достаточно `type`: даты, мастер и планы сохраняются как `null`,
  чек-лист копируется из активного шаблона. Индивидуальный список заменяет шаблон и не может быть пустым.
  Имя клиента ограничено 150 символами. Счета добавляются после создания.
  Заданный план работ, включая 0, создаёт одну строку без получателя и срока.
  Повтор с тем же ключом и другим телом возвращает конфликт.
- Использовать списки `/projects`, `/stages`, `/projects/{projectId}/stages`,
  справочник `/stage-types`, PATCH объекта/этапа, PUT состава чек-листа до старта.
- Панель получает `/dashboard/summary?through=YYYY-MM-DD` и `/dashboard/projects` независимо.
  Диапазон through — сегодня…+30 по UTC+5. Суммы возвращает сервер; неизвестный план — null.
- Пользователи имеют две роли: `manager` и `foreman`. Приёмку подтверждает руководитель.
- В выплате передавать обязательный `recipientId`; `recipient` в ответе всегда содержит пользователя.
  История получателей не меняется с назначением этапа.
  Публичный POST `/auth/password-reset-requests` не раскрывает существование пользователя.
- Фото загружается, завершается с `Idempotency-Key`, привязывается, затем пункт выполняется
  отдельным PATCH с актуальным `expectedVersion`. Повтор привязки не дублирует фото.
  Читать `photoCount`, `photosDeletedByRetention`, `reworkComment`.
  Удаление последнего фото выполненного пункта требует `confirmLastPhotoDeletion=true`.
- Приёмка не требует акта; paid подтверждает руководитель после приёмки и покрытия плана работ.
  При 409 перечитать ресурс и его версию; при переназначении прежний мастер получает 404.

Это перечень для отдельной разработки экранов, без изменений рукописного UI в этой фазе.

## Установка, резервная копия и восстановление

Начальная миграция `0000_initial.sql` создаёт текущую схему БД, справочник этапов,
шаблоны и триггеры. Установка выполняется на пустую БД командой `pnpm --dir api run db:migrate`;
повторный запуск сохраняет данные и не создаёт дополнительные шаблоны.
Первый manager создаётся локальной командой из `api/README.md` после миграций.

До изменения схемы остановить записи приложения, сделать согласованную копию PostgreSQL
и всего приватного S3-бакета. Копия только БД не восстанавливает фото, PDF и счета.
Сохранить также версию приложения/контрактов, конфигурацию хранения и секреты безопасным способом.
Проверять восстановление в отдельной среде с отдельным бакетом.

Пример команд PostgreSQL 18 при настроенном подключении через переменные PGHOST,
PGPORT, PGUSER, PGDATABASE и безопасный способ передачи пароля:

```sh
pg_dump --format=custom --file=stageby-backup.dump
createdb stageby_restore
pg_restore --exit-on-error --single-transaction --dbname=stageby_restore stageby-backup.dump
```

Восстановить копию бакета в отдельный бакет с исходными ключами объектов, включая pending-загрузки;
указать его и восстановленную БД в конфигурации API. До подключения клиентов проверить вход,
списки, деньги, скачивание фото и счетов, привязки и работу очистки. Копии и восстановление файлов
выполнять средствами выбранного S3-хранилища; не использовать публичный доступ к бакету.
Не запускать API до восстановления бакета, так как при старте подключается фоновая очистка.

После production-запуска откат схемы выполняется новой миграцией либо восстановлением
согласованной копии БД и файлов вместе с соответствующей версией приложения.
Не удалять применённые SQL-файлы или записи журнала Drizzle ради отката.
Перед переключением проверить восстановление; при сбое вернуть прежние подключения и версию,
оставив приложение остановленным до восстановления согласованности данных и файлов.

Известные ограничения: лимиты авторизации хранятся в памяти процесса (для нескольких экземпляров
нужно общее хранилище); подписанный URL действует до своего истечения, даже если авторизация
пользователя позже отозвана; API после отзыва не выдаёт новые URL. Очистка фото необратима без
резервной копии и сохраняет выполнение пункта (R16). Автоматическая доставка нового пароля,
акты приёмки, частичная оплата одного счёта и внешние интеграции не входят в объём.
Инструкция восстановления подготовлена; практическая проверка восстановления копии не выполнялась.
