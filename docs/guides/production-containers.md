# Локальная проверка production-контейнеров

Все команды выполняйте из корня репозитория с работающим Docker Engine в режиме
Linux-контейнеров. Сборка предназначена для `linux/amd64`.

## Какие контейнеры нужны

В рабочем окружении постоянно запущены три контейнера:

| Контейнер | Назначение |
| --- | --- |
| Web/Caddy | Принимает HTTPS, отдаёт фронт и направляет запросы в API |
| API | Выполняет серверную логику приложения |
| PostgreSQL | Хранит данные приложения |

Мигратор — отдельный кратковременный контейнер: он обновляет структуру БД перед
запуском новой версии и завершается. Собираются четыре образа: Web/Caddy, API,
мигратор и PostgreSQL 18.6 с pgBackRest 2.60.0 на основе официального образа.
Образ — шаблон; контейнер — запущенный экземпляр этого шаблона.

При обычной разработке продолжайте использовать `pnpm run dev` и корневой
`compose.yaml`. Группы `stageby-check-…` и `stageby-smoke-…` создаются только
командами проверок ниже и не являются дополнительными рабочими окружениями.

## Сборка и проверки

```sh
pnpm run production:check
pnpm run production:build
pnpm run production:smoke
```

Выполняйте команды последовательно. Во время `production:check` не запускайте
параллельно сборку образов или smoke-стенд: конкуренция за CPU может приводить
к таймаутам тестов.

`production:build` собирает все четыре образа с тегом `local`.
Версии Node.js, pnpm и digest базовых образов закреплены в
[`Dockerfile`](../../infrastructure/production/build/Dockerfile).
Базовый PostgreSQL закреплён по digest, пакет pgBackRest — по версии в
[`postgres.Dockerfile`](../../infrastructure/production/build/postgres.Dockerfile).

## Проверка pgBackRest

После сборки образа PostgreSQL выполните:

```sh
docker build --load --file infrastructure/minio/Dockerfile --tag stageby-minio:latest .
node infrastructure/production/checks/backrest.mjs stageby-postgres:local
```

Проверка запускает отдельные PostgreSQL и MinIO с временными секретами и TLS,
без опубликованных портов. Проверяются полный и дифференциальный бэкапы,
шифрование repository, отказ с неверным ключом и восстановление в новый том
до именованной точки WAL после последнего бэкапа. После завершения удаляются
только ресурсы тестового проекта. `release build` выполняет эту проверку
автоматически на собранном образе до smoke-проверки приложения и записывает
`checks.backup=passed` и версию pgBackRest в manifest.

Для включения архивирования на VPS используйте дополнительный файл
`runtime/backup.compose.yaml` вместе с основным Compose. Он добавляет PostgreSQL
исходящий доступ к S3, не публикует порт БД и сохраняет прежний том данных.
PostgreSQL получает `archive_mode=on`, `archive_timeout=300` и команду
`pgbackrest --stanza=stageby archive-push %p`.

Файл `/etc/stageby/pgbackrest.conf` должен существовать с правами root:root 0600.
Он монтируется только для чтения в `/run/stageby/pgbackrest.conf`; стартовый
скрипт копирует его в `/etc/pgbackrest/pgbackrest.conf` с владельцем postgres
и правами 0600 внутри контейнера, затем передаёт запуск штатному entrypoint.
После изменения файла на хосте пересоздайте контейнер, чтобы обновить его копию.
Не ослабляйте права файла на хосте. Для первого запуска задайте
`STAGEBY_ARCHIVE_MODE=off` только на время команды Compose, создающей PostgreSQL
с подключённой конфигурацией. Выполните `stanza-create` от postgres, чтобы
проверить доступ к бакету и создать stanza. После успеха пересоздайте PostgreSQL
с обоими Compose-файлами без этого временного значения: архивирование включится
по умолчанию. Затем выполните `check` и первый полный бэкап.
Локальная проверка воспроизводит эту последовательность и проверяет сохранение
данных при пересоздании контейнера. Команды первого переключения на VPS выдаются
отдельными шагами в [журнале развёртывания](../plans/production-deployment-journal.md).

При работе с настроенными бэкапами указывайте оба Compose-файла во всех командах,
которые создают или пересоздают PostgreSQL. Запуск только с основным файлом
вернёт конфигурацию без архивирования. Расписание бэкапов и внешний мониторинг
настраиваются отдельно; наличие образа и override-файла не подтверждает их готовность.

## Проверки приложения

`production:check` выполняет `pnpm run codegen`, затем `pnpm run check` в Linux
с отдельными временными PostgreSQL и MinIO. Generated-каталоги API и web, включая
маршруты, и bundle OpenAPI пересоздаются из исходников и не сравниваются с Git.
Проверка завершается ошибкой при изменении рукописных исходников, например после
исправлений линтеров; различия CRLF/LF не учитываются. Контейнеры и их данные
удаляются после проверки. Сервисы разработки не используются.

Контейнер проверок ограничен 2 CPU и 4 ГБ памяти. Node.js учитывает CPU-лимит
при автоматическом выборе числа работников линтеров и тестов.

`production:smoke` запускает отдельный Compose с пустой БД и случайными тестовыми
credentials. Проверяются миграции и их повторный запуск, HTTPS, маршруты, cookies,
Origin, ограничение входа при подмене forwarded-заголовков и readiness. Стенд
публикует только `127.0.0.1:18443`; сертификат локальный, его проверка отключена
только в клиенте этого сценария. После проверки стенд и временные файлы удаляются.

Команды `production:*` проверяют локальную сборку рабочей ветки. Для комплекта
релиза используйте отдельную команду ниже. Доставка и восстановление реализуются
по [плану](../plans/production-deployment.md).

## Сборка комплекта релиза

На компьютере разработчика должны быть доступны Git, авторизованный GitHub CLI
`gh` и Docker. В Windows используется системный `tar.exe`.

```sh
pnpm run release:test
pnpm run release build
```

Сборка разрешена только при чистом Git-состоянии, включая индекс и новые файлы.
`HEAD` должен быть итоговым коммитом объединённого PR в `main` репозитория
`origin` на GitHub и предком актуальной удалённой `main`. При недоступном GitHub
или неподтверждённом происхождении сборка прекращается.

Исходники извлекаются через `git archive` в отдельный временный каталог с LF.
Локальные `.env`, зависимости и игнорируемые файлы в него не попадают.
Из этого снимка последовательно выполняются Linux-проверки, сборка образов
`linux/amd64` и smoke-проверка. Образы приложения получают уникальный тег
релиза и метку Git SHA. PostgreSQL берётся по закреплённому digest.

Результат сохраняется в `docs/tmp/releases/<id>/`. Другой каталог задавайте
аргументом `--output <путь>` после `build`. Незавершённый комплект не публикуется.

| Файл | Назначение |
| --- | --- |
| `images.tar.gz` | Образы API, Web/Caddy, мигратора и PostgreSQL для `docker load` |
| `manifest.json` | Git SHA, PR, версии инструментов, ID образов, миграции и версия совместимости схемы, размеры и хеши файлов |
| `SHA256SUMS` | SHA-256 всех файлов комплекта, включая manifest |
| `release.env` | Теги образов без секретов |
| `runtime/` | Compose, Caddyfile и примеры конфигурации без credentials |

`release.env` задаёт `POSTGRES_IMAGE` на включённый в архив образ PostgreSQL.
Секреты приложения, мигратора и БД готовьте отдельно по разделу конфигурации ниже.
Размеры в manifest описывают архив и файлы; они не подтверждают достаточность
диска VPS для БД, WAL и трёх релизов.

`release:test` проверяет происхождение и упаковку на временных Git-репозиториях
с искусственными образами. Первый полный комплект из `main` собран из `1f8763d`
после PR #79; Linux- и smoke-проверки прошли. Результаты записаны в
[журнале развёртывания](../plans/production-deployment-journal.md).

## Состав и конфигурация

Файлы в `infrastructure/production/` сгруппированы по назначению:

| Каталог | Содержание |
| --- | --- |
| `build/` | Dockerfile и создание manifest схемы при сборке |
| `runtime/` | Compose приложения, Caddyfile и примеры конфигурации в `env/` |
| `migrations/` | Сценарий применения миграций в отдельном контейнере |
| `checks/` | Временный Compose и сценарий полного прогона проверок |
| `release/` | Проверка происхождения коммита, сборка и упаковка комплекта |

Команды запуска с компьютера разработчика находятся в корневом `scripts/`.

[`compose.yaml`](../../infrastructure/production/runtime/compose.yaml) использует готовые
образы, внешний S3 и постоянные тома PostgreSQL и Caddy. Он публикует только
порты Caddy 80/443. PostgreSQL находится в отдельной внутренней сети. API имеет
отдельную сеть для исходящих запросов к S3; Caddy доверен только по фиксированному
адресу `172.30.40.2` в сети прокси. Перед запуском проверьте отсутствие пересечения
подсети `172.30.40.0/24` с сетями хоста.

Для конфигурации задайте `RELEASE_ID` и абсолютный `STAGEBY_CONFIG_DIR`.
В каталоге конфигурации подготовьте `database.env`, `api.env`, `migrator.env`
по примерам из `infrastructure/production/runtime/env/`; подставьте credentials и ограничьте
права файлов. Секреты не входят в образы. Разделение прав пользователей БД,
бэкапы и подготовка сервера остаются отдельными пунктами плана; текущие примеры
подключения не подтверждают выполнение этих пунктов.

API работает от пользователя `node` с read-only файловой системой и tmpfs.
Миграции запускаются отдельным контейнером; API их автоматически не применяет.
Автозапуск контейнеров задан через `unless-stopped`; запуск Docker после
перезагрузки VPS проверяется при подготовке сервера.

## Маршруты и браузерная безопасность

Клиент обращается к `/api/...`; Caddy и dev proxy Vite удаляют `/api` перед
передачей запроса API. Прямые URL экранов возвращают HTML приложения. HTML требует
перепроверки актуальности, хешированные assets имеют immutable-кеш, ответы API —
`no-store`. Swagger выключен в production.

В Compose заданы `CORS_ORIGIN` и `API_PUBLIC_ORIGIN` равными
`https://pro-rab.net`, `S3_CREATE_BUCKET=false`, срок подписанных URL — 900 секунд.
Настройка CORS самого бакета описана в [руководстве S3](api-configuration.md#s3).

Caddy задаёт HSTS для HTTPS, `nosniff`, `Referrer-Policy: no-referrer` и Permissions
Policy. CSP работает в принудительном режиме; вход, навигация, фото, HEIC и PDF
проверены в Chromium с production-сборкой и тестовыми файлами Beget. Политика допускает
WASM без общего `unsafe-eval`, blob workers и previews, inline-стили атрибутов;
S3 разрешён только по точному origin провайдера.

`main.tsx` настраивает Zod с `jitless: true` до загрузки приложения: создание
объектных схем иначе вызывает пробу `Function` и нарушение CSP. Сохраняйте этот
порядок при изменении точки входа. Повторяйте браузерную проверку при изменении
политики, файловых сценариев или зависимостей, использующих workers/WASM.

## Готовность схемы и миграции

Внутренний `GET /health/live` проверяет процесс и не зависит от БД или S3.
`GET /health/ready` возвращает 200 только при доступной БД, завершённых обязательных
миграциях с ожидаемыми SHA-256 и совпадающей версии совместимости схемы.
Дополнительные завершённые миграции разрешены. Ошибки возвращают 503 без деталей
подключения. Caddy закрывает `/api/health` и вложенные пути от внешнего доступа.

Версия совместимости хранится в `api/schema-compatibility.json`; повышайте её
при несовместимых изменениях. При сборке создаётся `schema-manifest.json` с этой
версией и контрольными суммами SQL-миграций. Runtime API содержит только manifest,
скомпилированный код, production-зависимости и OpenAPI; SQL и мигратор находятся
в отдельном образе.

Мигратор получает advisory lock в PostgreSQL, проверяет историю и устанавливает
признак выполнения в `stageby_deployment.schema_state`. После успеха он обновляет
версию совместимости и снимает признак. При ошибке или прерывании признак остаётся:
readiness и следующий запуск мигратора завершаются ошибкой. Не снимайте его
автоматически: сначала сверяйте журнал миграций, контрольные суммы и фактическую
схему. Полная процедура восстановления незавершённого выпуска остаётся пунктом
плана до проверки аварийных сценариев.
