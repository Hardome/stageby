# План: деплой и сопровождение Stageby

Статус: запланирован.

## Цель

Подготовить воспроизводимую установку, выпуск, сопровождение и восстановление Stageby на чистом VPS с Ubuntu 26.04 LTS без GitHub Actions и платных сервисов GitHub.

Выбор входного веб-сервера и сравнение альтернатив описаны в [решении о Caddy](../decisions/production-reverse-proxy.md).

Согласованные условия:

- VPS: 2 CPU, 4 ГБ RAM; размер диска и архитектура уточняются перед подготовкой сервера.
- Одно production-окружение; при релизах допустим короткий простой до нескольких минут.
- Проверки и сборка выполняются на компьютере разработчика в Linux-контейнерах, доставка готовых образов — по SSH.
- Целевая потеря данных БД при аварии (RPO) — до 15 минут; целевое время восстановления (RTO) — до 4 часов. Достижимость подтвердить пробным восстановлением.
- Домен и внешний S3-провайдер пока не выбраны. На первом этапе файлы раздаются через HTTPS endpoint провайдера без собственного media-домена.
- Оповещения — в Telegram. Отдельный CI-сервер и тяжёлый стек мониторинга на старте не требуются.

| Компонент | Решение |
| --- | --- |
| Входящий трафик | Caddy: HTTPS, статика фронта, reverse proxy API |
| Backend | Контейнер с production-сборкой Node.js 24 |
| Frontend | Сборка Vite, раздаваемая Caddy |
| БД | PostgreSQL 18 в контейнере с постоянным томом |
| Фотографии и документы | Приватный внешний S3, прямые загрузки и скачивания по подписанным ссылкам |
| Бэкапы БД | pgBackRest: полные и дифференциальные копии, непрерывное архивирование WAL |
| Управление сервером | Ansible, SSH, systemd timers |
| Контроль состояния | Локальные проверки, внешний контроль heartbeat, Telegram |

Один VPS остаётся единой точкой отказа. Версии объектов S3 защищают от случайного удаления, но не заменяют независимую копию при потере хранилища или аккаунта. Цели RPO/RTO относятся к восстановлению после потери VPS при доступном внешнем хранилище.

## Изменения

### 1. Production-инфраструктура

- [ ] Подтвердить архитектуру VPS, размер диска и начальный объём данных; предусмотреть место для БД, WAL, логов и трёх комплектов релиза.
- [ ] Создать отдельный production Compose; текущий Compose сохранить для разработки, MinIO в production не запускать.
- [ ] Подготовить production-образы API, фронта с Caddy и мигратора; закрепить версии Node.js, pnpm и базовых образов, включая digest.
- [ ] Сохранить необходимые runtime-файлы API, включая используемый OpenAPI-контракт; миграции и инструменты мигратора упаковать отдельно от runtime API.
- [ ] Публиковать только порты Caddy 80/443. API и PostgreSQL подключить к внутренним сетям; доступ к БД предоставить только API и служебным задачам.
- [ ] Настроить постоянные тома PostgreSQL и данных Caddy, включая сертификаты; задать политики перезапуска и автозапуск после перезагрузки VPS.
- [ ] Запускать API без root, с read-only файловой системой, tmpfs для временных файлов, ограничениями ресурсов и без лишних Linux capabilities.
- [ ] Настроить ротацию логов и ограничения фоновых задач с учётом 2 CPU и 4 ГБ RAM.

### 2. Подготовка сервера и секреты

- [ ] Подготовить Ansible для установки Docker Engine и Compose, настройки каталогов, пользователей, firewall и systemd timers на Ubuntu 26.04 LTS.
- [ ] Настроить SSH по ключам, запретить парольный вход и root-login, завести отдельных пользователей администрирования и деплоя.
- [ ] Разрешить пользователю деплоя фиксированный серверный сценарий через sudo; доступ к Docker считать административным, Docker socket в контейнеры не передавать.
- [ ] Настроить firewall для IPv4 и IPv6: HTTP/HTTPS публично, SSH — по принятой политике доступа. Учесть обход UFW опубликованными Docker-портами.
- [ ] Включить обновления безопасности ОС без автоматической перезагрузки; перезагрузки проводить в окно обслуживания.
- [ ] Хранить секреты отдельно от Git, образов и релизных архивов в файлах с ограниченными правами; резервную копию секретов хранить зашифрованной вне VPS.
- [ ] Разделить учётные данные приложения, миграций и бэкапов; подготовить порядок их ротации.

### 3. Домен, маршрутизация и безопасность браузера

- [ ] Настроить DNS приложения на VPS и автоматический выпуск и продление HTTPS-сертификата Caddy.
- [ ] Раздавать фронт по `https://<домен>/`, API — по `https://<домен>/api/...`; Caddy удаляет `/api` перед передачей Fastify, внутренние пути API сохраняются.
- [ ] Установить базовый URL API-клиента `/api` и привести dev proxy к той же схеме; проверить ручные запросы и ссылки, чтобы пути фронта и API не пересекались.
- [ ] Обновить источники контрактов и выполнить codegen, если изменения затрагивают контракт; generated-файлы вручную не редактировать.
- [ ] Добавить внутренние `/health/live` и `/health/ready`: проверка процесса, доступности БД и соответствия схемы релизу. Проверять S3 отдельно от liveness API.
- [ ] Закрыть production Swagger от внешнего доступа.
- [ ] Задать `CORS_ORIGIN` и `API_PUBLIC_ORIGIN` точным HTTPS-origin приложения; сохранить проверку Origin для изменяющих запросов и cookies `Secure`, `HttpOnly`, `SameSite=Lax`.
- [ ] Ограничить `TRUST_PROXY` адресом Caddy в выделенной Docker-сети; проверить корректность клиентского IP и невозможность подмены forwarded-заголовков.
- [ ] Настроить CSP на HTML через Caddy: скрипты своего приложения, запрет inline-обработчиков, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, `form-action 'self'`.
- [ ] Разрешить в `connect-src` приложение и точный S3-origin; в `img-src` — приложение, S3 и используемые локальные previews. Проверить потребность обработки HEIC в workers/WASM, не вводить общее разрешение `unsafe-eval`.
- [ ] Для текущих inline-стилей компонентов предусмотреть отдельное разрешение `style-src-attr`, сохранив ограничения скриптов. Итоговую политику включить в принудительном режиме после браузерной проверки.
- [ ] После проверки HTTPS включить HSTS, настроить `nosniff`, `Referrer-Policy: no-referrer` и ограниченную Permissions Policy; исключить конфликтующие заголовки Caddy и API.
- [ ] HTML отдавать с перепроверкой актуальности, хешированные assets — с длительным immutable-кешем; API сохраняет `no-store`. Сохранять assets последних трёх релизов для открытых вкладок.

### 4. Внешний S3 и раздача файлов

- [ ] Выбрать провайдера с публично доступным HTTPS endpoint, приватными бакетами, CORS, подписанными URL, SHA-256 checksum и версиями объектов.
- [ ] Проверить на выбранном S3 реальный браузерный цикл: подписанный PUT, SHA-256 checksum, HEAD с checksum, подписанный GET и Content-Disposition.
- [ ] Настроить CORS бакета только для origin приложения: GET/HEAD/PUT и необходимые заголовки загрузки; проверить OPTIONS preflight.
- [ ] Ограничить ключ приложения нужным бакетом и операциями; запретить создание бакетов, изменение политик и окончательное удаление версий. В production отключить автоматическое создание бакета.
- [ ] Сохранить прямую раздачу файлов из S3 и срок подписанных ссылок 15 минут; учитывать, что выданная ссылка действует до истечения срока даже после выхода пользователя.
- [ ] Включить версии объектов с хранением предыдущих версий не менее 35 дней; согласовать lifecycle с окном восстановления БД.
- [ ] Описать и проверить восстановление версий файлов и снятие delete markers для объектов, необходимых восстановленной БД.

### 5. Бэкапы и восстановление PostgreSQL

- [ ] Подготовить образ PostgreSQL 18 с установленным pgBackRest и совместимыми версиями инструментов резервного копирования и восстановления.
- [ ] Создать отдельный S3-бакет backup repository вне VPS, предпочтительно в отдельном аккаунте; использовать отдельные credentials.
- [ ] Настроить клиентское шифрование repository; сохранить ключ шифрования и процедуру доступа вне VPS.
- [ ] Настроить полный бэкап еженедельно, дифференциальный ежедневно и непрерывное архивирование WAL.
- [ ] Установить PostgreSQL `archive_timeout=5min`; проверять доставку WAL во внешнее хранилище и предупреждать при задержке более 10 минут с учётом отсутствия активности БД.
- [ ] Настроить хранение базовых копий и WAL для восстановления минимум за 30 дней; очисткой управляет pgBackRest, без независимых lifecycle-правил, разрушающих цепочку восстановления.
- [ ] Контролировать накопление WAL и свободное место при недоступном S3; не удалять незаархивированные сегменты ради освобождения диска.
- [ ] До первого production-запуска выполнить полное восстановление на чистом временном сервере, измерить потерю данных и длительность.
- [ ] Подготовить ежемесячную проверку восстановления на отдельном временном сервере; включить проверку доступности файлов для восстановленной БД.

### 6. Выпуск и откат

Предоставить команды `release build`, `release deploy <id>`, `release rollback <id>` и `release status`. Сценарий, запускаемый с компьютера разработчика, должен работать в текущей Windows-среде с Docker и SSH.

- [ ] Разрешать сборку релиза только из чистого Git-состояния коммита, вошедшего в `main` через PR.
- [ ] Выполнять проверки и сборку в Linux-контейнерах под архитектуру VPS; интеграционные тесты запускать с временными PostgreSQL и S3.
- [ ] Останавливать выпуск при ошибках проверок, исправлениях линтеров или расхождении generated-файлов с исходным коммитом.
- [ ] Формировать комплект из готовых образов, manifest с Git SHA и версиями инструментов, контрольных сумм и production-конфигурации без секретов; registry не требуется.
- [ ] Передавать комплект по SSH во временный каталог VPS, проверять целостность и запрещать параллельный деплой серверной блокировкой.
- [ ] До обслуживания проверять свободное место, доступность БД, свежесть бэкапов и состояние архивирования WAL.
- [ ] Включать страницу обслуживания, корректно останавливать API, запускать отдельный мигратор один раз и применять только подготовленные миграции.
- [ ] Запускать новый комплект, проверять readiness и запросы через Caddy; после успеха снимать обслуживание и фиксировать текущий релиз.
- [ ] При ошибке приложения возвращать предыдущий комплект только при совместимости с применённой схемой; при ошибке миграции сохранять обслуживание для диагностики.
- [ ] Использовать расширение схемы с отдельным последующим удалением устаревшего; разрушительные миграции выпускать с отдельным сценарием восстановления. Автоматически старую БД при неудачном релизе не восстанавливать.
- [ ] Хранить последние три комплекта на VPS и их копии вне VPS; очистка не затрагивает текущий релиз и постоянные тома.
- [ ] Обновлять PostgreSQL отдельно от приложения; major-обновления проводить отдельной процедурой с проверенным восстановлением.

### 7. Мониторинг и эксплуатационная документация

- [ ] Настроить systemd timers для проверок API, БД, диска, памяти, сертификата, свежести бэкапов и архивирования WAL.
- [ ] Подключить внешний Healthchecks.io для контроля heartbeat и Telegram-оповещений: пропажа VPS также должна обнаруживаться. До настройки проверить актуальные условия бесплатного тарифа.
- [ ] Отправлять heartbeat успешного состояния только после соответствующих проверок; предусмотреть уведомления об отказе и восстановлении без постоянного повторения одинаковой ошибки.
- [ ] Исключить из уведомлений и логов секреты, session cookies и подписанные S3-ссылки.
- [ ] Описать еженедельный просмотр уведомлений и ёмкости, ежемесячные обновления и проверки восстановления, порядок обслуживания и перезагрузок.
- [ ] Подготовить инструкции первичной установки, релиза, отката, ротации секретов, обновления PostgreSQL и восстановления на чистом VPS в `docs/guides/`.
- [ ] Оформить принятое архитектурное решение в `docs/decisions/` по шаблону; обновить карту документации и необходимые тематические ссылки.

## Проверки и критерии завершения

- [ ] Чистый VPS подготавливается через Ansible; после перезагрузки приложение и служебные задачи запускаются автоматически.
- [ ] Из интернета недоступны БД, прямой API-порт и служебные интерфейсы; проверены IPv4 и IPv6.
- [ ] Работают HTTPS, обновление сертификата, cookies, CORS, отклонение чужого Origin и защита от поддельных proxy-заголовков.
- [ ] CSP не нарушает вход, навигацию, прямое открытие маршрутов, загрузку и просмотр фото, обработку HEIC и открытие PDF.
- [ ] Полный цикл загрузки и скачивания работает с выбранным production S3; анонимный доступ к приватным объектам без подписи запрещён.
- [ ] Успешно проверены обычный релиз и откат приложения, включая открытые вкладки предыдущей версии.
- [ ] Проверены обрыв SSH, повторный запуск выпуска, параллельный деплой, ошибка миграции и нехватка диска; неудачный выпуск не отмечается успешным.
- [ ] Проверена недоступность S3: отправляются уведомления, контролируется рост WAL, API не попадает в цикл перезапусков из-за liveness.
- [ ] Выполнено восстановление БД на выбранный момент; необходимые фотографии и документы доступны после восстановления версий S3.
- [ ] Измеренные RPO и RTO соответствуют 15 минутам и 4 часам на ожидаемом объёме данных либо зафиксированы необходимые изменения инфраструктуры.
- [ ] Telegram-уведомления приходят при остановке сервера, ошибках проверок и нарушении архивирования WAL, а также после восстановления.
- [ ] Завершена приёмка всего цикла; полезные сведения перенесены в постоянную документацию, план и отчёт приёмки удалены, ссылки обновлены без создания архива.

## Результаты

План сохранён; реализация инфраструктуры и проверки ещё не выполнялись. До установки необходимо выбрать домен и S3-провайдера, подтвердить архитектуру VPS и размер диска. Реальные RPO/RTO и достаточность ресурсов пока не проверены.

После полной приёмки сохранить архитектурные решения в `docs/decisions/`, инструкции в `docs/guides/`, удалить этот план и отчёт приёмки цикла и обновить ссылки. История остаётся в Git.
