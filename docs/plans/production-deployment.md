## Цель

Подготовить воспроизводимую установку, выпуск, сопровождение и восстановление Stageby на чистом VPS с Ubuntu 26.04 LTS без GitHub Actions и платных сервисов GitHub.

Выбор входного веб-сервера и сравнение альтернатив описаны в [решении о Caddy](../decisions/production-reverse-proxy.md).

Согласованные условия:

- VPS: Beget, Санкт-Петербург, Ubuntu 26.04 LTS; 2 CPU с частотой 3–3,3 ГГц,
  4 ГБ RAM, 40 ГБ NVMe, канал 1 Гбит/с; архитектура `x86_64`, целевая платформа
  контейнеров — `linux/amd64`.
- Начальный объём пользовательских данных БД и файлов — нулевой; перенос данных не требуется.
- Одно production-окружение; при релизах допустим короткий простой до нескольких минут.
- Проверки и сборка выполняются на компьютере разработчика в Linux-контейнерах, доставка готовых образов — по SSH.
- SSH и SCP используют парольную аутентификацию по выбору пользователя.
  Пароль вводится интерактивно; ключи не обязательны. Сохранять парольный вход
  и текущий доступ root; пароли не записывать в команды, файлы проекта и логи.
- Администрирование VPS, передача комплектов и деплой выполняются от root.
  Отдельные пользователи ОС и правила sudo для деплоя не требуются.
  Пользователи процессов внутри контейнеров определяются их конфигурацией;
  API продолжает работать от `node`. Учётные данные БД разделяются по назначению.
- Целевая потеря данных БД при аварии (RPO) — до 15 минут; целевое время восстановления (RTO) — до 4 часов. Достижимость подтвердить пробным восстановлением.
- Зарегистрирован домен `pro-rab.net`; origin приложения — `https://pro-rab.net`.
  Он заменяет ранее выбранный `stageby.ru`; CORS S3 перенастроен и проверен.
  Внешнее S3-хранилище — Beget; совместимость загрузок с MD5 проверена.
  Файлы раздаются через HTTPS endpoint провайдера без собственного media-домена.
- S3 endpoint: `https://s3.ru1.storage.beget.cloud`, бакет
  `0ac5f37cad2e-stageby-s3`. Регион для настройки клиента — `ru1` по
  [инструкции Beget](https://beget.com/ru/kb/faq/cloud/podklyuchenie-k-obektnomu-hranilishchu-s3-pri-pomoshchi-klientov-aws-cli-s3cmd-cyberduck-sdk).
  Приватность подтверждена проверкой доступа; бакет разрешён для тестов.
- Оповещения — в Telegram. Отдельный CI-сервер и тяжёлый стек мониторинга на старте не требуются.

| Компонент | Решение |
| --- | --- |
| Входящий трафик | Caddy: HTTPS, статика фронта, reverse proxy API |
| Backend | Контейнер с production-сборкой Node.js 24 |
| Frontend | Сборка Vite, раздаваемая Caddy |
| БД | PostgreSQL 18 в контейнере с постоянным томом |
| Фотографии и документы | Приватный внешний S3, прямые загрузки и скачивания по подписанным ссылкам |
| Бэкапы БД | pgBackRest: полные и дифференциальные копии, непрерывное архивирование WAL |
| Управление сервером | Ansible, SSH, systemd timers |
| Контроль состояния | Локальные проверки, внешний контроль heartbeat, Telegram |

Один VPS остаётся единой точкой отказа. Версии объектов S3 защищают от случайного удаления, но не заменяют независимую копию при потере хранилища или аккаунта. Цели RPO/RTO относятся к восстановлению после потери VPS при доступном внешнем хранилище.

## Порядок выполнения

Выполнять этапы последовательно. К следующему этапу переходить после проверки
результата предыдущего; production открывать пользователям после проверок
целевого окружения на этапе 6.

| Этап | Работы | Результат для перехода дальше |
| --- | --- | --- |
| 1. Уточнить окружение | Выбрать домен и S3, подтвердить архитектуру, диск и объём данных; проверить S3 по разделу 4 | Проверены загрузка, скачивание, checksum и восстановление версии объекта на выбранном S3 |
| 2. Собрать production локально | Подготовить образы, Compose, маршрутизацию и сборку релиза из разделов 1, 3 и 6 | Собранный комплект проходит проверки и запускается в Linux-контейнерах |
| 3. Подготовить временный VPS | Выполнить раздел 2, настроить DNS, HTTPS, бэкапы и мониторинг | Приложение доступно на тестовом домене, служебные порты закрыты, автозапуск и оповещения проверены |
| 4. Проверить выпуск | Реализовать и проверить деплой, откат и сбои из раздела 6 | Выпуск и откат воспроизводимы, обрыв SSH и повторный запуск не нарушают состояние |
| 5. Проверить восстановление | Восстановить БД и файлы на другом чистом VPS; завершить аварийные проверки | Пройдены технические проверки временного окружения, подтверждены RPO/RTO и инструкции восстановления |
| 6. Запустить production | Повторить установку на целевом VPS либо принять проверенный VPS; проверить рабочий домен и конфигурацию | Пройдены проверки целевого окружения, включены бэкапы и внешний мониторинг, завершена документация |

Для временного окружения использовать отдельные секреты, БД и бакеты с тестовыми
данными. После переноса на целевой VPS повторить проверки доступа, релиза,
бэкапов и оповещений; временные ресурсы удалить после приёмки.

## Проверки и критерии завершения

- [ ] Чистый VPS подготавливается через Ansible; после перезагрузки приложение и служебные задачи запускаются автоматически.
- [ ] Из интернета недоступны БД, прямой API-порт и служебные интерфейсы; проверены IPv4 и IPv6.
- [ ] Работают HTTPS, обновление сертификата, cookies, CORS, отклонение чужого Origin и защита от поддельных proxy-заголовков.
- [ ] CSP не нарушает вход, навигацию, прямое открытие маршрутов, загрузку и просмотр фото, обработку HEIC и открытие PDF.
- [ ] Полный цикл загрузки и скачивания работает с выбранным production S3; анонимный доступ к приватным объектам без подписи запрещён.
- [ ] Успешно проверены обычный релиз, откат после совместимого расширения схемы и отказ отката при несовместимой или незавершённой миграции.
- [ ] Проверены обрыв SSH при загрузке и во время миграции, повторный запуск выпуска, параллельный деплой, перезагрузка VPS во время выпуска, ошибка миграции и нехватка диска. Серверная операция переживает обрыв SSH; после перезагрузки доступен сохранённый этап и процедура восстановления; миграции не дублируются, неудачный выпуск не отмечается успешным.
- [ ] Проверена недоступность S3: отправляются уведомления, контролируется рост WAL, API не попадает в цикл перезапусков из-за liveness.
- [ ] Выполнено восстановление БД на выбранный момент; необходимые фотографии и документы доступны после восстановления версий S3.
- [ ] Измеренные RPO и RTO не превышают 15 минут и 4 часов на ожидаемом объёме данных. При превышении устранить причины и повторить восстановление; изменение целей требует явного согласования и обновления плана до приёмки.
- [ ] Telegram-уведомления приходят при остановке сервера, ошибках проверок и нарушении архивирования WAL, а также после восстановления.
- [ ] Внешняя HTTPS-проверка обнаруживает недоступность рабочего домена или публичного API при продолжающемся heartbeat VPS; проверены уведомления об отказе и восстановлении.
- [ ] Завершена приёмка всего цикла; полезные сведения перенесены в постоянную документацию, план и отчёт приёмки удалены, ссылки обновлены без создания архива.
