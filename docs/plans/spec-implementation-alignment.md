# План: согласование расхождений ТЗ и реализации

Дата сверки: 23.10.2026.
Статус: запланирован; ожидает согласования с заказчиком.

## Цель

Согласовать выявленные расхождения и уточнения, затем привести ТЗ, постоянную документацию, регрессионные чек-листы и при необходимости реализацию к единому поведению.

Зафиксированная ниже реализация установлена статическим чтением кода. Приложение в браузере в рамках сверки не прогонялось; документ не является отчётом об успешной приёмке или исчерпывающим перечнем дефектов.

До обсуждения с заказчиком исходное ТЗ и реализация по этому списку не изменяются. Описанное фактическое поведение не становится автоматически новым требованием. Предварительное направление — актуализировать ТЗ под реализацию, но итог по каждому вопросу фиксируется отдельно после согласования.

### Порядок согласования

Наиболее значимы DIF-01–DIF-06 и DIF-11: они затрагивают финансовые возможности и видимость сумм.

DIF-01–DIF-06 в основном соответствуют уже зафиксированным решениям о прямых выплатах этапа, расчёте сводки и автоматическом пересчёте статуса (R1, R11–R13 и уточнение от 18.10.2026). DIF-09 и DIF-10 согласуются с текущими правилами безопасности web. При этом DIF-08 расходится и с формулировкой R10 о сохранении с первого шага; обновления только исходного ТЗ недостаточно.

DIF-11 — отдельное функциональное расхождение между обещанной видимостью материалов и текущим экраном. Его нельзя считать исключительно устаревшим текстом без решения заказчика.

- [ ] Обсудить с заказчиком все DIF-01–DIF-20. Для каждого записать выбранное поведение, дату и основание согласования.
- [ ] Для каждого пункта определить действие: обновить ТЗ под реализацию, исправить реализацию либо уточнить формулировку без изменения поведения. Несогласованные пункты оставить открытыми.
- [ ] Обновить исходное ТЗ целиком по затронутым правилам и сценариям, включая перекрёстные ссылки и примеры; не ограничиваться добавлением новой оговорки рядом со старым противоречием.
- [ ] Синхронизировать согласованные решения, предметную модель и правила API/web там, где изменяется ожидаемое поведение.
- [ ] При необходимости изменить приложение и контракт; generated-файлы обновлять через codegen.
- [ ] Сверить ручные регрессионные чек-листы с итоговым решением по каждому пункту.

## Проверки и критерии завершения

- [ ] По всем 20 ID есть явное согласованное решение либо документированная передача в отдельную незавершённую задачу; отсутствие ответа не считается согласием.
- [ ] В ТЗ не осталось старых строк планирования, сроков обязательств, ручного подтверждения выплаты и запрета обратного перехода, если согласовано текущее поведение.
- [ ] Описание шагов формы, доступов, фото, таблицы, вкладок, лимитов и ярлыка соответствует выбранному поведению и фактической реализации.
- [ ] Проверены связанные вычисления и права: сводка к дате, получатель выплаты, переходы `completed`/`paid`, завершение объекта, видимость сумм мастеру.
- [ ] Выполнен целевой ручной регресс согласованных сценариев; если код изменялся, пройдены соответствующие автоматизированные проверки. Зафиксированы версия приложения, окружение и ограничения проверки.
- [ ] Завершена приёмка всего цикла. Итоговые требования и решения сохранены в постоянной документации; этот план и отчёт приёмки цикла удалены, ссылки обновлены без создания архива.

## Результаты

Сохранён перечень 20 вопросов по результатам статической сверки. Решения заказчика по этому перечню пока не получены. ТЗ, правила, регрессионные чек-листы и код в рамках записи перечня не изменены; проверка в браузере и приёмка не выполнялись.

После полной приёмки сохранить согласованные правила в `docs/rules/` и решения в `docs/decisions/`, удалить этот план и отчёт приёмки цикла и обновить ссылки. История остаётся в Git.
