# План доработок бэкенда по обновлённому edited.ver2

## 1. Документ и согласованные решения

Дата плана — 12.10.2026. Основание — текущая редакция [ТЗ edited.ver2](ТЗ%20на%20разработку%20страницы%20и%20сценарии%20edited.ver2.md) и сравнение с действующей реализацией. Существующий завершённый план сохраняется как история.

`[ ]` означает предстоящую задачу; `[x]` — реализованную и проверенную.

Вопросы и полученные ответы:

| Вопрос | Принятое решение |
| --- | --- |
| Требуется перенос существующих объектов и выплат? | Нет. Целевая установка — БД без прикладных данных |
| Можно увеличивать план выплаченного этапа? | Только если остаток работ остаётся ≤ 0. Нарушающее условие изменение блокируется |
| Как показывать незаданный план? | Сохранить `null` для соответствующего плана и остатка, отдельно показывать факт и неполноту плана |
| Можно менять получателя строки после выплат? | Да. Получатели прошлых выплат сохраняются; новый получатель применяется к будущим выплатам |
| Можно восстановить исключённый этап? | Да, восстановлением той же записи. Минимум один включённый этап обязателен |
| Как сохранять форму редактирования объекта? | Одним атомарным запросом; ошибка любой части отменяет все изменения |
| Кто задаёт планы этапов и как получить общий план объекта? | Планы работ и материалов — хранимые nullable-поля этапа, руководитель редактирует их вручную. Общие планы объекта вычисляются из планов включённых этапов, не редактируются и не хранятся в БД. Факты вычисляются из выплат и оплаченных счетов |

Объём реализации: API, исходники OpenAPI, БД, аудит, документация и тесты. Рукописный UI не входит; сгенерированный клиент web обновляется вместе с контрактом.

## 2. Модель данных и финансовые правила

- [x] Добавить строки плана работ: ID, этап, плановая сумма, nullable-получатель, nullable-срок выплаты, версия и служебные даты.
- [x] Привязать выплату к строке своего этапа; сохранить отдельного получателя выплаты. Получатель берётся из строки при создании выплаты.
- [x] Сохранить `plannedWorkAmountMinor` и `plannedMaterialAmountMinor` как ручные nullable-поля этапа, редактируемые только руководителем. Общие планы объекта вычислять из планов включённых этапов; агрегаты не редактировать и не хранить в БД.
- [x] При создании этапа сохранить ручной план работ на этапе и дополнительно создать одну строку без получателя и срока выплаты. При незаданном плане строку не создавать.
- [x] Запретить удаление строки с выплатами. Распределение строки без получателя и выплат выполнять атомарно: сумма новых строк равна исходной, исходная строка удаляется с сохранением аудита.
- [x] Разрешить смену и очищение получателя строки без изменения прошлых выплат. Новая выплата требует выбранного активного мастера.
- [x] Для `paid` сохранять инвариант: план работ задан, остаток ≤ 0. Проверять его при правках и удалениях планов и выплат; нарушение возвращает конфликт без изменения статуса.
- [x] Разрешить правки дат, назначенного мастера и планов после старта, включая `completed` и `paid`, с указанным финансовым ограничением. Фактические даты сохраняются.
- [x] Сделать даты этапа независимо nullable. Каждую заданную дату проверять относительно обеих границ проекта; порядок дат проверять только при наличии обеих.
- [x] Добавить включённость этапа и девятый справочный тип `additional` без шаблона. Сохранить уникальность типа внутри объекта; дополнительный этап располагается последним.
- [x] В счёте сохранить сумму выставления отдельно от nullable-фактической суммы и календарной даты оплаты. Время и автор отметки остаются служебными данными; при снятии оплаты фактическая сумма и дата очищаются.

Суммы сохраняют существующий формат в копейках и ограничения целых рублей. План строки может быть нулевым, выплата и фактическая оплата счёта — положительные. Сроки выплат не ограничиваются датами проекта; календарные даты трактуются по Екатеринбургу.

ручных планов включённых этапов; строки выплат их не заменяют.

## 3. API и серверное поведение

### Создание объекта — §3.4 ТЗ

- [x] Актуализировать контракт `POST /projects` и серверную валидацию формы из двух шагов «Объект» и «Этапы»: реквизиты объекта, выбранные стандартные этапы, их даты, мастер, планы и индивидуальные чек-листы.
- [x] Сохранить обязательность клиента, адреса, координат и обеих дат проекта. Требовать минимум один включённый стандартный этап; повторные типы и тип `additional` при создании запрещены.
- [x] Разрешить отсутствие и независимое очищение дат этапа. Неуказанные даты, мастер и планы сохраняются как `null`; заданные даты проверяются относительно сроков проекта.
- [x] Обеспечить быстрое создание с первого шага и создание с любого экрана этапа: форма передаёт все включённые этапы, включая ещё не открытые пользователем. Для неоткрытых этапов используются стандартные типы, шаблонные пункты и незаданные даты, мастер и планы. Не переданный в список создания этап считается исключённым и не создаётся.
- [x] Если индивидуальный чек-лист этапа не передан, копировать активный шаблон; если передан — сохранять его вместо шаблона. Пустой индивидуальный список отклонять. Изменения не затрагивают справочник и другие объекты.
- [x] Введённые руководителем планы работ и материалов сохранять в nullable-полях этапа. При заданном плане работ дополнительно создавать строку без получателя и срока выплаты, даже если мастер этапа выбран. При плане `null` строка отсутствует; при плане 0 создаётся строка с нулевым планом.
- [x] Сохранить поддержку предварительно загруженных PDF проекта: пустой список допустим, файлы проверяются до создания. Счета материалов добавляются только после создания объекта и не входят в составной запрос.
- [x] Создавать объект, этапы, чек-листы, строки плана и связи документов в одной транзакции с аудитом. Ошибка любого этапа отменяет всю операцию.
- [x] Сохранить идемпотентность повторной отправки после обрыва связи, включая новые финансовые записи. Ошибки возвращать с путями полей и индексами этапов, чтобы форма могла открыть экран с первой ошибкой.
- [x] После создания возвращать актуальный объект и вычисленные финансовые итоги. Переход на дашборд и сохранение введённых данных между экранами относятся к отдельной реализации UI.

### Дашборд

Общие планы объекта = суммы ручных планов включённых этапов; они вычисляются, не редактируются
и не хранятся в БД. План выплат к D по срокам строк ниже — отдельный расчёт обязательств,
который не заменяет ручные планы этапов и общие планы объекта.

- [x] Работы отбирать по сроку строки, иначе по окончанию этапа. Без обеих дат строка исключается; явный срок всегда имеет приоритет.
- [x] Материалы отбирать по окончанию этапа, использовать ручной план материалов.
- [x] Факт ограничивать датой оплаты ≤ D и теми же строками или этапами, которые вошли в план. Оплата не уменьшает план.
- [x] Остаток считать как план минус факт, сохраняя отрицательные значения.
- [x] Если у включённого в расчёт этапа нет строк работ, но окончание ≤ D, считать его план работ неизвестным. Незаданный план материалов также даёт `null`; общий план неизвестен при неизвестности составляющей.
- [x] Этапы без начала сортировать в конце. Исключённые этапы не участвуют в финансовых расчётах, выборе текущего этапа и активном счётчике.

Дашборд реализован 12.10.2026. Сводка считает обязательства работ по строкам,
материалы — по ручным планам этапов, факт — по датам оплаты в том же периметре.
Общие планы объекта по-прежнему вычисляются из ручных планов включённых этапов.
Обновлены OpenAPI и сгенерированные API/web-файлы. Проверены сроки до/в/после D,
авансы, приоритет срока строки, отсутствие дат, неизвестные и нулевые планы,
полная оплата, переплата, исключённые этапы и сортировка без начала.
Выполнены `pnpm run codegen` и `pnpm run check`: API — 184 теста,

### Редактирование объекта и этапов — §3.5 ТЗ

Строки оплаты изменять с их ID и версиями, без замены существующих строк с выплатами одной нераспределённой строкой.
- [x] Добавить версию проекта; составное сохранение проверяет версии проекта и изменяемых вложенных ресурсов. Изменения включённости увеличивают версию проекта.
- [x] Проверять итоговое состояние всей формы перед сохранением. Обновить SQL-проверки дат так, чтобы корректное совместное изменение сроков объекта и этапов не блокировалось промежуточным состоянием.
- [x] Исключение разрешать только до фактического старта и без фото, счетов и выплат. Наличие связанных записей фото, включая удалённые, блокирует исключение.
- [x] Восстановление возвращает прежнюю запись, планы и чек-лист после проверки актуальных дат и назначения. Исключённый дополнительный этап восстанавливается вместо создания второго.
- [x] Добавление дополнительного этапа разрешать только при редактировании, в том числе завершённого объекта, с обязательным непустым индивидуальным чек-листом.
- [x] Состав чек-листа блокировать по `actualStartDate`, независимо от снятия отметок. Дополнительный этап участвует в завершении; после его добавления завершённый объект возвращается в активные.

Для частичных обновлений отсутствие поля означает «сохранить», `null` — «очистить». Архивные объекты сохраняют действующий запрет изменений.
