# План доработок бэкенда по обновлённому edited.ver2

## 1. Документ и согласованные решения

Дата плана — 12.10.2026. Основание — текущая редакция [ТЗ edited.ver2](ТЗ%20на%20разработку%20страницы%20и%20сценарии%20edited.ver2.md) и сравнение с действующей реализацией. Существующий завершённый план сохраняется как история.

`[ ]` означает предстоящую задачу; `[x]` — реализованную и проверенную.

Вопросы и полученные ответы:

| Вопрос | Принятое решение |
| --- | --- |
| Требуется перенос существующих объектов и выплат? | Нет. Целевая установка — БД без прикладных данных |
| Можно увеличивать план выплаченного этапа? | Только если остаток работ остаётся ≤ 0. Нарушающее условие изменение блокируется |
| Как показывать незаданный план? | Сохранить `null` для соответствующего плана и остатка, отдельно показывать факт и неполноту плана |
| Можно менять получателя строки после выплат? | Да. Получатели прошлых выплат сохраняются; новый получатель применяется к будущим выплатам |
| Можно восстановить исключённый этап? | Да, восстановлением той же записи. Минимум один включённый этап обязателен |
| Как сохранять форму редактирования объекта? | Одним атомарным запросом; ошибка любой части отменяет все изменения |

Объём реализации: API, исходники OpenAPI, БД, аудит, документация и тесты. Рукописный UI не входит; сгенерированный клиент web обновляется вместе с контрактом.

## 2. Модель данных и финансовые правила

- [ ] Добавить строки плана работ: ID, этап, плановая сумма, nullable-получатель, nullable-срок выплаты, версия и служебные даты.
- [ ] Привязать выплату к строке своего этапа; сохранить отдельного получателя выплаты. Получатель берётся из строки при создании выплаты.
- [ ] Убрать хранимый общий план работ этапа. В ответах сохранить агрегат `plannedWorkAmountMinor`, вычисляемый из строк; без строк он равен `null`.
- [ ] При создании этапа преобразовывать введённый общий план в одну строку без получателя и срока выплаты. При незаданном плане строку не создавать.
- [ ] Запретить удаление строки с выплатами. Распределение строки без получателя и выплат выполнять атомарно: сумма новых строк равна исходной, исходная строка удаляется с сохранением аудита.
- [ ] Разрешить смену и очищение получателя строки без изменения прошлых выплат. Новая выплата требует выбранного активного мастера.
- [ ] Для `paid` сохранять инвариант: план работ задан, остаток ≤ 0. Проверять его при правках и удалениях планов и выплат; нарушение возвращает конфликт без изменения статуса.
- [ ] Разрешить правки дат, назначенного мастера и планов после старта, включая `completed` и `paid`, с указанным финансовым ограничением. Фактические даты сохраняются.
- [ ] Сделать даты этапа независимо nullable. Каждую заданную дату проверять относительно обеих границ проекта; порядок дат проверять только при наличии обеих.
- [ ] Добавить включённость этапа и девятый справочный тип `additional` без шаблона. Сохранить уникальность типа внутри объекта; дополнительный этап располагается последним.
- [ ] В счёте сохранить сумму выставления отдельно от nullable-фактической суммы и календарной даты оплаты. Время и автор отметки остаются служебными данными; при снятии оплаты фактическая сумма и дата очищаются.

Суммы сохраняют существующий формат в копейках и ограничения целых рублей. План строки может быть нулевым, выплата и фактическая оплата счёта — положительные. Сроки выплат не ограничиваются датами проекта; календарные даты трактуются по Екатеринбургу.

## 3. API и серверное поведение

### Создание объекта — §3.4 ТЗ

- [ ] Актуализировать контракт `POST /projects` и серверную валидацию формы из двух шагов «Объект» и «Этапы»: реквизиты объекта, выбранные стандартные этапы, их даты, мастер, планы и индивидуальные чек-листы.
- [ ] Сохранить обязательность клиента, адреса, координат и обеих дат проекта. Требовать минимум один включённый стандартный этап; повторные типы и тип `additional` при создании запрещены.
- [ ] Разрешить отсутствие и независимое очищение дат этапа. Неуказанные даты, мастер и планы сохраняются как `null`; заданные даты проверяются относительно сроков проекта.
- [ ] Обеспечить быстрое создание с первого шага и создание с любого экрана этапа: форма передаёт все включённые этапы, включая ещё не открытые пользователем. Для неоткрытых этапов используются стандартные типы, шаблонные пункты и незаданные даты, мастер и планы. Не переданный в список создания этап считается исключённым и не создаётся.
- [ ] Если индивидуальный чек-лист этапа не передан, копировать активный шаблон; если передан — сохранять его вместо шаблона. Пустой индивидуальный список отклонять. Изменения не затрагивают справочник и другие объекты.
- [ ] Введённый при создании план работ сохранять одной строкой без получателя и срока выплаты, даже если мастер этапа выбран. При плане `null` строка отсутствует; при плане 0 создаётся строка с нулевым планом. План материалов сохранять отдельно на этапе.
- [ ] Сохранить поддержку предварительно загруженных PDF проекта: пустой список допустим, файлы проверяются до создания. Счета материалов добавляются только после создания объекта и не входят в составной запрос.
- [ ] Создавать объект, этапы, чек-листы, строки плана и связи документов в одной транзакции с аудитом. Ошибка любого этапа отменяет всю операцию.
- [ ] Сохранить идемпотентность повторной отправки после обрыва связи, включая новые финансовые записи. Ошибки возвращать с путями полей и индексами этапов, чтобы форма могла открыть экран с первой ошибкой.
- [ ] После создания возвращать актуальный объект и вычисленные финансовые итоги. Переход на дашборд и сохранение введённых данных между экранами относятся к отдельной реализации UI.

### Финансы и права

- [ ] Добавить CRUD строк плана и отдельную атомарную операцию распределения. Существующий API выплат принимает ID строки; её принадлежность этапу проверяется сервером.
- [ ] Чтение строк и выплат разрешить руководителю и назначенному мастеру. Мастер видит собственные строки и отдельно собственные выплаты, в том числе после смены получателя строки.
- [ ] Прямые запросы к чужим финансовым ресурсам возвращают `404`. После снятия назначения доступ к финансам этапа прекращается.
- [ ] Общие итоги назначенного этапа рассчитывать по всем строкам и выплатам. Мутации финансов доступны только руководителю.
- [ ] При отметке оплаты счёта требовать фактическую сумму и дату; факт материалов считать по этой сумме.

### Дашборд

- [ ] Работы отбирать по сроку строки, иначе по окончанию этапа. Без обеих дат строка исключается; явный срок всегда имеет приоритет.
- [ ] Материалы отбирать по окончанию этапа, использовать ручной план материалов.
- [ ] Факт ограничивать датой оплаты ≤ D и теми же строками или этапами, которые вошли в план. Оплата не уменьшает план.
- [ ] Остаток считать как план минус факт, сохраняя отрицательные значения.
- [ ] Если у включённого в расчёт этапа нет строк работ, но окончание ≤ D, считать его план работ неизвестным. Незаданный план материалов также даёт `null`; общий план неизвестен при неизвестности составляющей.
- [ ] Этапы без начала сортировать в конце. Исключённые этапы не участвуют в финансовых расчётах, выборе текущего этапа и активном счётчике.

### Редактирование объекта и этапов — §3.5 ТЗ

- [ ] Обеспечить загрузку данных для заполнения тех же двух шагов формы: реквизитов и документов объекта, параметров включённых этапов, индивидуальных чек-листов, строк плана и версий. Руководителю также отдавать исключённые этапы для восстановления; обычные списки включённых этапов их не показывают.
- [ ] Расширить `PATCH /projects/{projectId}` составным сохранением реквизитов, параметров этапов, чек-листов, включённости, строк плана работ и дополнительного этапа. Отсутствие этапа в частичном запросе не означает исключение: изменение включённости передаётся явно.
- [ ] В форме редактирования общий план работ показывать как итог строк. Правки плана сохранять через строки с их ID и версиями, без второго редактируемого общего поля и без замены существующих строк с выплатами одной нераспределённой строкой.
- [ ] Добавить версию проекта; составное сохранение проверяет версии проекта и изменяемых вложенных ресурсов. Изменения включённости увеличивают версию проекта.
- [ ] Проверять итоговое состояние всей формы перед сохранением. Обновить SQL-проверки дат так, чтобы корректное совместное изменение сроков объекта и этапов не блокировалось промежуточным состоянием.
- [ ] Исключение разрешать только до фактического старта и без фото, счетов и выплат. Наличие связанных записей фото, включая удалённые, блокирует исключение.
- [ ] Восстановление возвращает прежнюю запись, планы и чек-лист после проверки актуальных дат и назначения. Исключённый дополнительный этап восстанавливается вместо создания второго.
- [ ] Добавление дополнительного этапа разрешать только при редактировании, в том числе завершённого объекта, с обязательным непустым индивидуальным чек-листом.
- [ ] Состав чек-листа блокировать по `actualStartDate`, независимо от снятия отметок. Дополнительный этап участвует в завершении; после его добавления завершённый объект возвращается в активные.
- [ ] Все изменения, включая распределение плана и побочные изменения, фиксировать в одной транзакции аудита. Блокировки согласовать между составным сохранением и отдельными операциями ресурсов.

Для частичных обновлений отсутствие поля означает «сохранить», `null` — «очистить». Архивные объекты сохраняют действующий запрет изменений.

## 5. Проверки и критерии готовности

- [ ] Быстрое создание со всеми восемью стандартными этапами и создание с любого экрана этапа: неоткрытые этапы получают шаблоны и незаданные параметры.
- [ ] Создание с выбранными этапами и изменёнными чек-листами: исключённые этапы не создаются, справочник и шаблоны не меняются; пустой список этапов, дубли типов и дополнительный этап отклоняются.
- [ ] При создании выбран мастер и задан план: появляется одна нераспределённая строка, мастер автоматически не становится получателем; незаданный и нулевой планы различаются.
- [ ] Ошибка реквизитов, даты, чек-листа или файла при создании отменяет объект и все вложенные записи; повтор успешного запроса не дублирует объект, строки плана и документы.
- [ ] Загрузка и повторное сохранение формы редактирования сохраняют ID строк плана, выплат и этапов; частичный запрос не исключает непереданные этапы.
- [ ] Четыре комбинации дат, отдельное очищение, обе границы проекта, совместное изменение сроков.
- [ ] Создание нераспределённого плана, нулевой и незаданный план, распределение без двойного учёта, запрет выплаты без получателя.
- [ ] Смена получателя с сохранением истории и правильной видимостью прошлых выплат.
- [ ] План и факт к D: приоритет срока строки, аванс, оплаты до/в/после D, полная оплата и переплата.
- [ ] Различие суммы счёта и оплаты, отсутствие влияния счетов на ручной план материалов.
- [ ] Правки выплаченного этапа: допустимые изменения и отказ при нарушении финансового инварианта.
- [ ] Исключение, восстановление, запрет исключения последнего этапа и этапа с ресурсами; конкурентные операции.
- [ ] Единственный дополнительный этап, отсутствие шаблона, повторное открытие и завершение объекта.
- [ ] Атомарный откат формы, конфликты версий, аудит всех побочных изменений.
- [ ] Регрессия: фото без «Готово», неизменность фактического старта, запрет правки состава после старта, отзыв доступа мастера.
- [ ] Чистая установка и повторное применение миграций, тесты API, codegen, проверки типов и сборки API и web.

Готовность: новые сценарии проходят через HTTP и PostgreSQL; контракты и документация согласованы; производные суммы вычисляются из первичных данных; generated-файлы не редактируются вручную.
