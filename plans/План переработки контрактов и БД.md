# План переработки контрактов и БД по новому ТЗ

## 1. Цель

Привести OpenAPI-контракт и схему PostgreSQL к требованиям из
`plans/ТЗ на разработку страницы и сценарии.md` для первой версии Stageby:

- руководитель управляет всеми объектами, этапами, суммами, счетами и выплатами;
- мастер работает только со своими этапами и видит деньги только внутри них;
- объект создаётся вместе с выбранными этапами, сроками и индивидуальными чек-листами;
- выполнение пунктов подтверждается фотографиями;
- учитываются планы и факты по работам и материалам;
- дашборд руководителя получает готовые серверные агрегаты и вычисляемые задачи.

План охватывает контракты, БД, миграции, серверные правила и проверку результата. Реализация UI в него не входит.

## 2. Зафиксированные продуктовые решения

1. Руководитель видит деньги по всем объектам и этапам. Мастер видит суммы только назначенного ему этапа.
2. Плановая сумма материалов вводится руководителем вручную.
3. Фактическая сумма материалов вычисляется как сумма оплаченных счетов этапа.
4. Нехватка материалов закрывается отдельной явной отметкой, а не появлением нового счёта.
5. Загрузка фотографии не выполняет пункт автоматически. После успешной загрузки пользователь явно нажимает «Готово».
6. У этапа только один мастер. Отдельная сущность бригады в первой версии не требуется.
7. Плановая сумма этапа попадает в сводку по плановой дате окончания этапа.
8. Объект имеет четыре агрегированных статуса: `created` — создан, `in_progress` — в работе, `acceptance` — приёмка, `completed` — выполнен. Статуса «Передан клиенту» нет. Статус объекта вычисляется по фактическому старту этапов и состоянию последнего включённого этапа.
9. Адрес, широта и долгота обязательны при создании объекта.
10. У объекта нет отдельного обязательного названия: его идентифицируют имя клиента и адрес.
11. Седьмой тип этапа называется `finishing` / «Отделка» вместо `plaster` / «Штукатурка».
12. Денежные суммы на границе frontend/API и в БД всегда передаются и хранятся в минимальных единицах валюты — копейках. В БД используется `bigint`, в OpenAPI — неотрицательный `integer` с `format: int64`; денежные поля имеют суффикс `AmountMinor`. UI принимает и показывает целые рубли, перед отправкой умножает значение на 100, после получения делит на 100. В первой версии записываемые суммы должны быть кратны 100. Значение `null` означает, что план ещё не задан; ноль не подменяет отсутствие плана.
13. Файлы физически хранятся в объектном хранилище. PostgreSQL содержит только метаданные, связи и состояние загрузки.
14. У этапа может быть несколько заказов материалов, у каждого заказа — несколько счетов. Для статуса `supplied` нужен минимум один заказ, у каждого заказа должен быть минимум один счёт, и все счета всех заказов этапа должны быть отмечены доставленными.
15. Отклонение план-факт на сегодня вычисляется как `(план − факт) / план × 100`: положительное значение означает экономию, ноль — соответствие плану, отрицательное — перерасход. При нулевом, отсутствующем или неполном плане значение не вычисляется и возвращается как `null`.
16. Максимальный размер одной фотографии до клиентского сжатия — 20 МБ. Максимальный размер файла счёта — 50 МБ.
17. К одному пункту чек-листа можно привязать не более 20 активных фотографий. Удалённая фотография освобождает место.
18. Файловое хранилище использует S3-совместимый интерфейс: production — S3-хранилище Beget, локальная разработка и интеграционные тесты — MinIO в Docker Compose. Bucket закрытый, постоянные публичные URL не используются.
19. Типы этапов хранятся в таблице-справочнике `stage_types`, а не в PostgreSQL enum. В первой версии публичного API управления справочником нет.
20. Email в системе не используется. Пользователь входит по уникальному логину, учётные записи создаёт администратор, самостоятельной регистрации нет.

## 3. Целевая предметная модель

### 3.1 Проект

Расширить `projects`:

- `plannedStartDate date not null`;
- `plannedEndDate date not null`;
- `address`, `latitude`, `longitude` сделать обязательными;
- сохранить имя клиента в `ownerName`;
- удалить отдельное поле `title`: у объекта нет самостоятельного обязательного названия помимо клиента и адреса;
- для списков и карточек возвращать `ownerName` и `address`, а отображаемую подпись собирать из них без сохранения дублирующего значения;
- не хранить редактируемые плановые и фактические итоги — вычислять их по этапам, платежам и счетам;
- статус проекта вычислять сервером и возвращать как read-only поле.

Проверки БД:

- окончание проекта не раньше начала;
- координаты находятся в допустимых диапазонах;
- даты каждого этапа находятся внутри сроков проекта;
- проект содержит хотя бы один этап.

Последнее правило проверяется транзакцией создания, потому что межтабличное ограничение нельзя надёжно выразить обычным `CHECK`.

### 3.2 Типы и экземпляры этапов

Целевой справочник:

1. `foundation` — Фундамент;
2. `walls` — Стены;
3. `roof` — Крыша;
4. `windows` — Окна;
5. `facade` — Фасад;
6. `electrical` — Электрика;
7. `finishing` — Отделка;
8. `heating` — Отопление.

Создать таблицу-справочник `stage_types`:

- `code varchar primary key` — стабильный неизменяемый код, используемый в API;
- `title varchar not null` — отображаемое название;
- `position integer not null unique` — порядок по умолчанию;
- `isActive boolean not null default true`;
- `createdAt`, `updatedAt`.

`stages.stageTypeCode` ссылается на `stage_types.code` с `ON DELETE RESTRICT`. Деактивированный тип остаётся доступен в существующих объектах, но не может быть добавлен в новый объект. Код типа после создания не редактируется; меняются только название, позиция и активность. Публичного CRUD для справочника в первой версии нет: начальные значения создаются seed-миграцией, административные изменения выполняются вне пользовательского интерфейса.

Изменить `stages`:

- заменить `plaster` на `finishing`;
- добавить статус `rework` и `paid`;
- удалить отдельный статус `started`, сопоставив существующие записи с `in_progress`;
- оставить одного `assigneeId`;
- сделать плановые даты обязательными;
- добавить `canRunInParallel boolean not null default false` либо сохранить более точную модель предшественников и вычислять флаг для UI;
- добавить `plannedWorkAmountMinor bigint`;
- добавить `plannedMaterialAmountMinor bigint`;
- сохранить `actualStartDate` и `actualEndDate` как серверные поля;
- продолжить использовать `version` для оптимистической блокировки.

Целевая цепочка статусов:

```text
created -> assigned -> supplied -> in_progress -> acceptance -> completed -> paid
                                      ^              |
                                      |              v
                                      +----------- rework
```

Правила переходов:

- `created -> assigned`: руководитель назначил активного пользователя с ролью мастера;
- `assigned -> supplied`: у этапа есть хотя бы один счёт и все существующие счета отмечены доставленными; пустой набор счетов условие не выполняет;
- `assigned|supplied -> in_progress`: явно завершён первый пункт чек-листа; сервер фиксирует `actualStartDate`;
- `in_progress -> acceptance`: явно завершены все пункты непустого чек-листа;
- `acceptance -> rework`: руководитель указал комментарий, новый срок и хотя бы один пункт;
- `rework -> acceptance`: повторно завершены все отмеченные для доработки пункты;
- `acceptance -> completed`: руководитель подтвердил приёмку;
- `completed -> paid`: руководитель выполняет переход, а сервер проверяет, что остаток по работам равен нулю.

### 3.3 Шаблоны и чек-листы

Добавить таблицы шаблонов:

- `checklist_templates`: один активный шаблон на тип этапа;
- `checklist_template_items`: название, фотоподсказка и позиция.

При создании проекта шаблон копируется в обычные `checklists` и `checklist_items`. Дальнейшее редактирование экземпляра не меняет шаблон.

Изменить `checklist_items`:

- убрать ограничение позиции `1..4`;
- поддержать минимум один пункт на включённый этап при создании проекта;
- добавить `photoHint varchar(1000)`;
- добавить состояние доработки, например `requiresRework boolean` и `reworkComment` либо связь с последней записью приёмки;
- сохранить автора и время явного выполнения.

Прогресс вычисляется сервером как `round(completed / total * 100)` до целого числа. Пустой чек-лист имеет прогресс 0 и не может перейти на приёмку.

### 3.4 Файлы и фотографии

Добавить `files`:

- `id`;
- `storageKey` — уникальный внутренний ключ;
- `originalName`;
- `mimeType`;
- `sizeBytes`;
- `checksum`;
- `status`: `pending`, `uploaded`, `failed`, `deleted`;
- `uploadedByUserId`;
- `createdAt`, `uploadedAt`, `expiresAt`, `deletedAt`.

Добавить связи:

- `project_documents(projectId, fileId, position)` — PDF проекта, несколько файлов;
- `checklist_item_photos(checklistItemId, fileId, position)` — JPEG, PNG или HEIC;
- файл счёта связывается с `material_invoices`.

Правила:

- проектный файл: только PDF, не более 50 МБ;
- счёт: PDF или JPEG, не более 50 МБ;
- фото: JPEG, PNG или HEIC, не более 20 МБ до клиентского сжатия;
- не более 20 активных фотографий на один пункт чек-листа; лимит проверяется атомарно при привязке;
- ограничения MIME и размера проверяются при создании upload-сессии и повторно при её завершении по фактически загруженному объекту;
- `expiresAt` фотографии устанавливается на один год после успешной загрузки;
- удаление просроченных фото выполняет фоновая задача, после успешного удаления объект помечается `deleted`;
- удаление последней фотографии завершённого пункта атомарно снимает отметку после подтверждения пользователя;
- прямые публичные URL в API не возвращаются; просмотр и скачивание требуют авторизации.

Для устойчивости к плохой связи использовать двухфазную загрузку: создать upload-сессию, загрузить содержимое, подтвердить завершение. Повтор завершения с тем же ключом идемпотентности не создаёт второй файл.

Окружения используют один S3-совместимый адаптер:

- production — закрытый bucket в S3-хранилище Beget;
- локальная разработка и интеграционные тесты — MinIO через Docker Compose;
- endpoint, region, bucket и credentials задаются конфигурацией окружения;
- клиент получает только короткоживущие подписанные данные для загрузки или скачивания;
- бизнес-код не зависит от конкретного поставщика S3.

### 3.5 Оплата работ

Добавить `work_payments`:

- `id`;
- `stageId`;
- `paidAt date`;
- `amountMinor bigint`;
- `comment varchar(1000)`;
- `createdByUserId`;
- `createdAt`, `updatedAt`;
- `version` для конкурентного изменения.

План работ хранится на этапе в копейках. Факт работ — сумма `amountMinor` платежей. Остаток — `plan - fact`; отрицательное значение означает переплату. Платёж должен быть строго больше нуля и в первой версии кратен 100 копейкам.

### 3.6 Материалы и счета

Добавить `material_orders`:

- `id`;
- `stageId`;
- `sentAt`;
- `sentByUserId`;
- `createdAt`, `updatedAt`;
- `version`.

Один этап может иметь несколько заказов. Ограничение уникальности по `stageId` не добавляется.

Добавить `material_invoices`:

- `id`, `orderId`, `fileId`;
- необязательное имя поставщика;
- `amountMinor bigint not null`;
- `paidAt`, `paidByUserId`;
- `deliveredAt`, `deliveredByUserId`;
- `createdAt`, `updatedAt`, `version`.

Статус «Выставлен счёт» является фактом наличия успешно загруженного счёта. Оплата и доставка — независимые серверные признаки, потому что доставка не должна стирать информацию об оплате.

Добавить `material_shortages`:

- `id`, `invoiceId`;
- обязательный комментарий до 500 символов;
- `reportedAt`, `reportedByUserId`;
- `resolvedAt`, `resolvedByUserId`;
- `resolutionComment`;
- `version`.

Новая накладная или счёт не закрывает нехватку. Закрытие выполняется отдельной операцией руководителя.

### 3.7 Запрос сброса пароля

Вход и восстановление работают по логину, email в модели отсутствует:

- сохранить `users.login` и его уникальность;
- нормализовать логин по действующим правилам до сохранения и поиска;
- учётные записи создаёт администратор, публичной регистрации нет;
- добавить `password_reset_requests` с пользователем, временем запроса и временем обработки;
- публичный запрос принимает логин и не раскрывает, существует ли такая учётная запись;
- руководитель видит необработанный запрос и устанавливает новый пароль существующей операцией;
- смена пароля отзывает все сессии пользователя.

## 4. Изменения OpenAPI

Исходники изменяются только в `contracts/references/`. `contracts/openapi.yaml`, API-типы и web-клиент регенерируются командой `pnpm run codegen`.

### 4.1 Проекты

Переделать `CreateProject` в атомарный составной запрос:

```yaml
clientName: string
address: string
coordinates: { latitude, longitude }
plannedStartDate: date
plannedEndDate: date
documentFileIds: integer[]
stages:
  - type: StageType
    plannedStartDate: date
    plannedEndDate: date
    canRunInParallel: boolean
    assigneeId: integer | null
    plannedWorkAmountMinor: integer | null
    plannedMaterialAmountMinor: integer | null
    checklistItems:
      - title: string
        photoHint: string | null
```

Требования операции:

- минимум один этап;
- уникальный тип и позиция этапа;
- минимум один пункт на этап;
- все даты этапов внутри дат проекта;
- создание проекта, этапов и чек-листов выполняется одной транзакцией;
- повторную отправку формы и двойной клик предотвращает frontend; серверная идемпотентность создания объекта не входит в текущий объём.

`GET /projects` и `GET /projects/{projectId}` доступны руководителю. Мастер получает данные объекта только через представление назначенного этапа, без сумм других этапов.

### 4.2 Этапы и деньги

Расширить `Stage`:

- новый enum типа и статуса;
- целочисленный прогресс;
- `plannedWorkAmountMinor`, `actualWorkAmountMinor`, `workBalanceMinor`;
- `plannedMaterialAmountMinor`, `actualMaterialAmountMinor`;
- `totalPlannedAmountMinor`, `totalActualAmountMinor`;
- краткая сводка счетов, доставки и открытых нехваток;
- признак просрочки как вычисляемое read-only поле.

Финансовые поля возвращаются руководителю для любого этапа и мастеру только для назначенного ему этапа. Сам доступ к чужому этапу мастера возвращает `404`, чтобы не раскрывать существование записи.

Добавить операции:

```text
GET    /stages/{stageId}/work-payments
POST   /stages/{stageId}/work-payments
PATCH  /work-payments/{paymentId}
DELETE /work-payments/{paymentId}

GET    /stages/{stageId}/material-orders
POST   /stages/{stageId}/material-orders
PATCH  /material-orders/{orderId}

GET    /material-orders/{orderId}/invoices
POST   /material-orders/{orderId}/invoices
PATCH  /material-invoices/{invoiceId}

POST   /material-invoices/{invoiceId}/shortages
POST   /material-shortages/{shortageId}/resolution
```

Мастер может менять только доставку и создавать сообщение о нехватке на своём этапе. Оплату счёта, плановые суммы, платежи и устранение нехватки меняет руководитель.

### 4.3 Чек-листы и фото

Сохранить явную операцию изменения пункта, но усилить правила:

- `isCompleted: true` допускается только при наличии хотя бы одного файла со статусом `uploaded`;
- операция является явным нажатием «Готово» и не вызывается автоматически после загрузки;
- `isCompleted: false` снимает отметку и пересчитывает статус/прогресс согласно допустимому состоянию этапа;
- к пункту можно привязать не более 20 активных фотографий; двадцать первая отклоняется с `409 photo_limit_exceeded`;
- пункты на приёмке доступны мастеру только для чтения;
- после возврата на доработку мастер меняет только отмеченные руководителем пункты.

Добавить:

```text
GET    /checklist/items/{itemId}/photos
POST   /checklist/items/{itemId}/photos
DELETE /checklist/photos/{photoId}
```

### 4.4 Загрузка и скачивание файлов

Добавить ресурс загрузки:

```text
POST /file-uploads
PUT  /file-uploads/{uploadId}/content
POST /file-uploads/{uploadId}/completion
GET  /files/{fileId}/content
```

Если будет выбрано S3-совместимое хранилище, `POST /file-uploads` может возвращать короткоживущие подписанные данные для загрузки. Контракт не должен раскрывать постоянный внутренний storage URL.

Ошибки должны различать неподдерживаемый MIME, превышение размера, незавершённую загрузку, несовпадение checksum и истёкшую upload-сессию.

### 4.5 Дашборд

Разделить данные на независимые запросы, чтобы ошибка карточек не блокировала таблицу:

```text
GET /dashboard/summary?through=YYYY-MM-DD
GET /dashboard/tasks
GET /dashboard/projects?limit=...&offset=...
```

`summary` возвращает:

- количество активных объектов;
- неоплаченный план работ по этапам с `plannedEndDate <= through`;
- неоплаченный план материалов по тем же этапам;
- общий план;
- отклонение план-факт на текущую дату.

`tasks` возвращает вычисляемые задачи:

- отправить заказ за семь дней до старта;
- запросить счёт для каждого заказа через два дня после отправки, если у него нет счетов;
- проверить открытую нехватку;
- назначить мастера за семь дней до старта.

Задачи не имеют операции ручного закрытия. В ответе должны быть `type`, `stageId`, `projectId`, `dueDate`, `isOverdue` и данные для отображения.

`projects` возвращает оптимизированную проекцию строки дашборда, а не полную карточку проекта. Сортировка по умолчанию — дата начала проекта по убыванию, затем ID для стабильности.

### 4.6 Пользователи и авторизация

- сохранить вход по логину и не добавлять email в пользовательские схемы;
- оставить создание учётных записей администратору, без публичной регистрации;
- добавить `POST /auth/password-reset-requests` с логином и нейтральным ответом без раскрытия существования пользователя;
- добавить фильтр необработанных запросов на странице пользователей либо отдельный manager-only список;
- документировать возврат на исходную страницу после повторного входа как ответственность клиента через безопасный локальный route, а не произвольный внешний URL.

## 5. Производные расчёты

Все расчёты выполняются сервером и одинаково используются в API и дашборде.

```text
actualWorkAmountMinor      = SUM(work_payments.amountMinor)
workBalanceMinor           = plannedWorkAmountMinor - actualWorkAmountMinor
actualMaterialAmountMinor  = SUM(material_invoices.amountMinor WHERE paidAt IS NOT NULL)
stagePlannedAmountMinor    = plannedWorkAmountMinor + plannedMaterialAmountMinor
stageActualAmountMinor     = actualWorkAmountMinor + actualMaterialAmountMinor
progressPercent     = ROUND(completedItems * 100 / totalItems)
```

Если одна из плановых сумм не задана, API должен отдельно сообщать неполноту плана; `null` нельзя незаметно считать нулём в итогах дашборда.

Статус проекта вычисляется по включённым этапам с приоритетом от конечного состояния к начальному:

- `completed`: последний включённый по позиции этап имеет статус `paid`;
- `acceptance`: последний включённый по позиции этап имеет статус `acceptance` или `completed` и ещё не выплачен;
- `in_progress`: хотя бы один включённый этап фактически начат, но условия `acceptance` и `completed` ещё не выполнены; доработка последнего этапа также относится к `in_progress`;
- `created`: ни один включённый этап ещё фактически не начат.

Назначение мастера, создание заказа, загрузка счёта и доставка материалов сами по себе не меняют агрегированный статус объекта. До фактического старта работ объект остаётся в `created`, поскольку отдельного агрегированного статуса для подготовки нет.

Отклонение план-факт рассчитывается на одном и том же финансовом периметре на текущую дату:

```text
variancePercent = (plannedAmount - actualAmount) / plannedAmount * 100
```

- план 1 000 000 ₽, факт 900 000 ₽ — `+10%`, экономия;
- план 1 000 000 ₽, факт 1 000 000 ₽ — `0%`;
- план 1 000 000 ₽, факт 1 100 000 ₽ — `-10%`, перерасход;
- план равен нулю, отсутствует или неполон — `variancePercent: null`.

## 6. План миграции БД

Миграцию выполнять поэтапно, не изменяя существующие миграции задним числом.

### Этап A. Подготовка

1. Добавить новые таблицы, включая `stage_types`, и nullable-колонки.
2. Добавить новые значения enum, где это возможно без замены типа.
3. Создать индексы и внешние ключи.
4. Развернуть код, способный читать старую и новую форму данных, если в окружении уже есть реальные записи.

### Этап B. Перенос данных

1. Заполнить `stage_types` восемью утверждёнными значениями, включая `finishing` / «Отделка», и перевести ссылки существующих этапов с `plaster` на `finishing`.
2. Сопоставить `started` с `in_progress`.
3. Заполнить сроки проекта из минимальной/максимальной даты этапов; при отсутствии использовать подтверждённое ручное значение, а не выдуманную дату.
4. Найти проекты без адреса или координат и сформировать отчёт для ручного исправления.
5. Засеять шаблоны чек-листов из утверждённого списка ТЗ.
6. Существующие индивидуальные чек-листы не заменять шаблонными.

### Этап C. Ужесточение ограничений

После успешного backfill:

1. Сделать обязательными адрес, координаты и сроки проекта.
2. Сделать обязательными даты этапов.
3. Удалить старый enum типов этапа после перевода `stages` на внешний ключ `stage_types.code`; enum статусов заменить новым PostgreSQL type через явный `USING CASE`.
4. Удалить ограничения чек-листа `3..4` и позиции `1..4`.
5. Добавить `CHECK` для положительных платежей, счетов и неотрицательных планов.
6. Проверить отсутствие осиротевших файлов и несогласованных статусов.

### Этап D. Очистка

1. После перехода контрактов и всего кода удалить устаревшую колонку `projects.title`.
2. Удалить совместимость со старым enum и старым форматом создания проекта.
3. Обновить Drizzle snapshot и тест миграций с чистой БД и с данными предыдущей версии.

## 7. Индексы и конкурентность

Добавить индексы минимум на:

- `stages(assigneeId, status, plannedStartDate)`;
- `stages(projectId, position)`;
- `stages(plannedEndDate, status)` для финансовой сводки;
- `work_payments(stageId, paidAt)`;
- `material_orders(stageId, sentAt)`;
- `material_invoices(orderId, paidAt, deliveredAt)`;

Все изменения статуса, завершение пункта, удаление последнего фото, добавление платежа и отметка оплаты счёта выполняются в транзакции. Для изменяемых ресурсов используется `expectedVersion`; конфликт возвращает `409 version_conflict`.

## 9. Проверки

### 9.1 Контракт

- Redocly lint и bundle проходят без ошибок;
- нет неразрешённых `$ref` и повторяющихся `operationId`;
- все операции имеют схемы `400`, `401`, `403/404`, `409` и при необходимости `413`;
- пагинация, порядок и фильтры описаны явно;
- generated API и web-типы совпадают с исходным OpenAPI.

### 9.2 БД и миграции

- миграции проходят на пустой БД;
- миграции проходят поверх снимка предыдущей версии с тестовыми данными;
- rollback-план документирован для шагов до ужесточения `NOT NULL`;
- суммы не теряют точность;
- каскады не удаляют финансовую историю случайно;
- пользователь, связанный с платежом, счётом или фото, не удаляется физически.

### 9.3 Интеграционные сценарии

- повторную отправку формы создания объекта блокирует frontend;
- нельзя создать объект без адреса, координат, сроков или этапов;
- шаблон копируется, а изменение чек-листа объекта не меняет шаблон;
- мастер не видит чужой этап и суммы проекта;
- фото без «Готово» не выполняет пункт;
- без загруженного фото выполнить пункт нельзя;
- двадцать первая активная фотография пункта отклоняется, в том числе при конкурентной загрузке;
- завершение первого пункта устанавливает фактический старт;
- завершение последнего пункта переводит этап на приёмку;
- возврат на доработку открывает только отмеченные пункты;
- несколько платежей корректно формируют факт и переплату;
- неоплаченный счёт не входит в факт материалов;
- несколько заказов этапа и несколько счетов каждого заказа учитываются независимо;
- закрытие нехватки требует отдельного действия;
- дашборд учитывает план по дате окончания этапа;
- архивные или недоступные записи не попадают в агрегаты;
- конкурентные изменения возвращают предсказуемый `409`.
