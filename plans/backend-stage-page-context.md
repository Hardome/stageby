# API: контекст для страницы этапа

Статус: выполнен. Использование контекста на странице передано отдельному исполнителю в рамках [плана 04](frontend-ver2/04-stage-page.md). Приоритет: P0.

## Вывод исходного анализа

До реализации доработка API была необходима: `Stage` не содержал документов и плановых границ проекта, телефона назначенного мастера и порядкового номера среди включённых этапов. Эти поля добавлены по плану ниже.

Источники проверки:

- `contracts/references/stages/stages.yaml`: `Stage` содержит `projectId`, адрес и координаты, но не документы и даты проекта. `position` — фиксированная позиция типа, а не номер среди включённых этапов.
- `contracts/references/users/users.yaml`: `Stage.assignee` использует `UserBrief`, в котором есть только `id` и `fullName`.
- `api/src/modules/stages/repository.ts`: `loadStages` уже читает проект и назначенного пользователя; списки для мастера ограничены его назначениями. Из такого списка нельзя вычислить номер среди всех включённых этапов объекта.
- `api/src/modules/files/repository.ts`: `getDownload` уже разрешает мастеру получение PDF, если у него есть назначенный этап проекта. В `files.test.ts` проверены доступ и его отзыв после переназначения. Не хватает получения ID документов через доступный ответ этапа.
- `docs/api-contract.md`: `getProject` доступен только руководителю. Открывать его мастеру ради страницы этапа не требуется.
- ТЗ ver2, §3.5.2: телефон мастера и просмотр PDF входят в состав страницы. Границы дат нужны редактору руководителя; порядковый номер зафиксирован как требование плана 04.

Все исходные данные уже есть в `projects`, `users`, `project_documents`, `files` и `stages`. Новые таблицы и миграции не нужны. Изменения касаются контракта чтения, сборки ответа и проверок; правила `updateStage` уже поддерживают редактирование параметров страницы.

## Предлагаемый контракт

Расширить существующий `Stage`, сохранив текущие поля и операции. Отдельный endpoint не нужен: контекст должен быть доступен при прямом открытии `getStage`, а общая схема уже используется списками и ответами мутаций.

| Поле | Тип и смысл |
| --- | --- |
| `projectDocumentFileIds` | Обязательный массив ID загруженных PDF текущего проекта, в порядке `project_documents.position ASC`, затем ID связи. `[]` означает, что прикреплённых загруженных документов нет. |
| `projectPlannedStartDate` | Обязательная дата `YYYY-MM-DD`, нижняя граница плановых дат этапа. |
| `projectPlannedEndDate` | Обязательная дата `YYYY-MM-DD`, верхняя граница плановых дат этапа. |
| `includedStageNumber` | Обязательное nullable-поле: номер этапа с 1 среди всех включённых этапов проекта по `position ASC`, затем ID. Для исключённого этапа, доступного руководителю, — `null`. |
| `includedStageCount` | Обязательное целое 1–9: количество всех включённых этапов проекта, включая дополнительный и этапы других мастеров. |
| `assignee.phone` | Обязательное nullable-поле внутри назначенного мастера; отсутствие телефона — `null`, отсутствие назначения — прежнее `assignee: null`. |

Для `assignee` ввести отдельную схему `StageAssignee` с `id`, `fullName`, `phone`. Не расширять общий `UserBrief`: это потребовало бы телефона в несвязанных ответах о выполнении пунктов, приёмке и других пользователях. Ограничения телефона взять из существующей схемы пользователя.

Новые поля описать как read-only. Не добавлять их в запросы изменения этапа. `position` сохраняет существующее значение. Например, при включённых типах с позициями 1, 3 и 9 дополнительный этап получает `includedStageNumber: 3`, `includedStageCount: 3`, `position: 9`.

Возвращать ID файлов, а временную ссылку получать через существующий `getFileContent` при открытии или скачивании. Не включать storage key и заранее созданные ссылки в `Stage`.

- [x] Не соединять документы напрямую с основным запросом этапов так, чтобы несколько PDF дублировали строки или финансовые итоги. Не добавлять запросы для каждого отдельного этапа.

- [x] Отдавать актуальный контекст после изменения документов, дат проекта, телефона и включённости. Эти изменения не обязаны менять `Stage.version`; `expectedVersion` продолжает защищать запись этапа, а сервер проверяет даты по текущим границам проекта.

### 3. Интеграционные проверки

- [x] Руководитель и назначенный мастер получают одинаковый контекст доступного этапа; посторонний мастер не получает его.
- [x] Ноль, один и несколько PDF; порядок документов; исключение незавершённых загрузок; полученные ID открываются через `getFileContent`.
- [x] Телефон задан, отсутствует и изменён; мастер не назначен. В ответе нет логина и других полей полного пользователя.
- [x] Границы проекта актуальны после редактирования; nullable-даты этапа сохраняются; сервер отклоняет дату за пределами актуальных границ независимо от клиентской проверки.
- [x] Нумерация при пропущенных типах, исключении и восстановлении, дополнительном этапе; для мастера с одним назначением учитываются все включённые этапы объекта. Для исключённого этапа руководителя номер `null`.
- [x] Списки и ответы мутаций соответствуют расширенной схеме; несколько документов не дублируют этапы и не меняют финансовые итоги.
- [x] После переназначения прежний мастер получает `404` при чтении этапа и запросе новой ссылки PDF, если у него больше нет назначений в проекте. При сохранении другого назначения доступ к общим PDF сохраняется. Уже выданная временная ссылка действует по существующему TTL — мгновенный отзыв ссылок в эту задачу не входит.
- [x] Архивный проект доступен для разрешённого чтения; запрет изменений сохраняется.

Расширить существующие `stages.test.ts` и `files.test.ts`, используя общие фикстуры и текущую настройку интеграционной БД.

## Критерий закрытия зависимости

Проверки реализации: контракт и генерация, lint, типы и сборки API/web выполнены; 222 теста API и 296 тестов web прошли. Миграции применены автоматически к отдельной тестовой БД. Новые миграции для этой доработки не требуются.

Контракт, генерация и интеграционные проверки выполнены; затем фронтенд проверяет четыре пункта зависимости и отмечает готовность плана 04.
