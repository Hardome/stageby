# 06. Оплата работ

Приоритет: P0 / сквозные требования первой итерации.

Источник: [ТЗ ver2](<../ТЗ на разработку страницы и сценарии edited.ver2.md>), §3.6, финансовые ограничения §1.4.

[Общий план](<../Общий план фронтенда по ТЗ ver2.md>) · [Оглавление](README.md)

## Текущее состояние

- [x] Ручной план работ редактируется в формах объекта. Есть клиент строк плана, распределения, выплат и перехода paid. Рабочий блок оплаты отсутствует.

## Зависимости

[План 04](04-stage-page.md); приёмка перед подтверждением выплаты — [план 10](10-acceptance-and-rework.md).

## Цель

Планировать выплаты и вести фактические платежи внутри этапа.

## Изменения

- [ ] Реализовать блок строк: план, получатель, необязательный срок, фактические платежи и остаток.
- [ ] Добавить создание и изменение строки, выбор или очистку получателя и срока.
- [ ] Руководителю разрешить удаление строки без выплат и распределение строки без получателя и выплат. Сумма распределения должна совпадать с исходной.
- [ ] Добавить создание, изменение и удаление платежей с датой, положительной суммой и комментарием.
- [ ] Даты строк и платежей не ограничивать сроками проекта.
- [ ] Имена получателей строк для руководителя получать через доступный ему API пользователей; учитывать исторических неактивных получателей. Мастер видит своё имя из сессии.
- [ ] Для мастера отдельно отображать собственные выплаты, сохранившие его получателя, даже если исходная строка стала недоступна.
- [ ] Общие итоги брать из этапа; собственную детализацию мастера не выдавать за полный факт строки или этапа.
- [ ] Различать ручной план этапа и итог строк планирования выплат.
- [ ] Добавить подтверждение `paid` только при `completed`, заданном плане работ и остатке ≤ 0.
- [ ] Обрабатывать отказ изменения или удаления выплаты, нарушающей ограничения выплаченного этапа.

## API и интерфейсы

Операции строк плана и распределения, операции выплат, `changeStageStatus({ status: 'paid' })`. План строки неотрицателен; выплата положительна. Получатель выплаты сохраняется сервером независимо от текущего получателя строки.

## Проверки и критерии готовности

- [ ] Нулевой план строки и положительная сумма выплаты.
- [ ] Дробление оплаты на несколько платежей, переплата, срок вне проекта.
- [ ] Смена и очистка получателя после выплат.
- [ ] Собственная историческая выплата при чужой текущей строке.
- [ ] Атомарное распределение без удвоения плана; запрет удаления строки с выплатами.
- [ ] Ранняя оплата не меняет статус; явная выплата после приёмки.
- [ ] Начальная строка после создания объекта при плане `0`, положительном плане и `null`.
- [ ] Изменения выплаченного этапа допустимы только при сохранении заданного плана работ и остатка ≤ 0.

## Общие правила

- Использовать существующие React, TanStack Router/Query, React Hook Form, контрактные схемы и UI-компоненты.
- Маршруты размещать в `app/routes`, сборку экранов — в `pages`, действия — в отдельных фичах с публичным `index.ts`. Общие данные этапа, права и инвалидирование запросов — в `entities/stage`, когда появится повторное использование.
- Проверять идентификаторы до запроса. Состояние списков и выбранную дату дашборда хранить в URL.
- Показывать начальную загрузку, пустое состояние, ошибку с повтором и фоновое обновление. При ошибке сохранения сохранять ввод; конфликт версии требует обновления данных.
- Использовать серверные статусы и агрегаты. Деньги передавать в копейках, `null` отличать от нуля, отрицательный остаток показывать как переплату.
- После действий обновлять затронутые запросы этапа, чек-листа, материалов, выплат, объекта, списка мастера и дашборда.
- Проверять светлую и тёмную темы, клавиатурный фокус и ширины 390/768/1024/1440 px.
- Генерируемые файлы обновлять через кодогенерацию. Комментарии в коде писать по-русски.
- Серверные доработки не входят в эти планы. Недостающие данные API фиксировать как внешнюю зависимость, не заменять вымышленными данными.
