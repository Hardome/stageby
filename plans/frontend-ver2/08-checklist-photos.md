## Изменения

- [ ] Добавить `/stages/$stageId/checklist/$itemId/photos`; проверить принадлежность пункта загруженному чек-листу.
- [ ] Реализовать камеру, галерею, множественный выбор, подсказку к фото и сетку из трёх колонок.
- [ ] Проверять исходные JPEG/PNG/HEIC до 20 МиБ; резервировать места с учётом активных и ожидающих фото.
- [ ] JPEG/HEIC готовить к отправке как JPEG, PNG с прозрачностью сохранять как PNG. Базовый предел длинной стороны — 2560 px, качество JPEG — 0,85.
- [ ] HEIC конвертировать на клиенте через лениво подключаемый `heic-to`; библиотека поддерживает преобразование HEIC в JPEG/PNG. [Документация проекта](https://github.com/hoppergee/heic-to).
- [ ] Реализовать цепочку: подготовка → upload-сессия → PUT → завершение загрузки → привязка файла к пункту.
- [ ] Сохранять результат каждого шага для повтора. Успешно привязанные фото не загружать повторно.
- [ ] Очередь незавершённых файлов и идентификаторы операций хранить в IndexedDB с привязкой к пользователю и пункту. При истечении сессии приостанавливать; продолжать после входа тем же пользователем. При явном выходе или смене пользователя очищать.
- [ ] «Готово» отправляет `updateChecklistItem` с актуальной версией только после успешной привязки допустимого фото. Выход без кнопки сохраняет фото без новой отметки выполнения.
- [ ] Добавить полноэкранный просмотр со смахиванием, удаление и подтверждение последнего фото через `confirmLastPhotoDeletion=true`.
- [ ] Не показывать автора и время фото. Для доработки после удаления старых фото требовать новое.
- [ ] При отказе хранилища сохранить текущую очередь в памяти и явно предупредить, что перезагрузка потеряет незавершённые файлы.

## API и интерфейсы

Операции загрузки файлов, список/привязка/удаление фото, `getFileContent`, `updateChecklistItem`.

Подготовку изображения отделить от upload-пайплайна. Контрольная сумма, имя, MIME и размер upload-сессии должны соответствовать подготовленному файлу. Для повтора сохранять fileId, upload-сессию, ключ завершения и состояние привязки; короткоживущие ссылки обновлять при необходимости.

## Проверки и критерии готовности

- [ ] Обрыв на каждом шаге, повтор без дублей, истечение подписанной ссылки.
- [ ] Двадцать первое фото и конкурентный отказ лимита.
- [ ] Выход без «Готово», повторное открытие и восстановление после входа.
- [ ] Удаление последнего фото с отказом и подтверждением.
- [ ] HEIC на телефоне, отказ камеры, просмотр со смахиванием.
- [ ] Приёмка, доработка, истечение хранения и новые фото.
- [ ] Восстановление очереди после перезагрузки; смена пользователя не раскрывает чужие файлы.
- [ ] Ошибка или недоступность IndexedDB не блокирует работу в текущей вкладке.

## Выбранные значения по умолчанию

Конвертация HEIC выполняется на клиенте. Предел длинной стороны 2560 px и качество JPEG 0,85 — базовые настройки подготовки фото; их читаемость проверяется на реальных фотографиях строительных работ. Полноценная фоновая загрузка при закрытом приложении не входит в план.

## Общие правила

- Использовать существующие React, TanStack Router/Query, React Hook Form, контрактные схемы и UI-компоненты.
- Маршруты размещать в `app/routes`, сборку экранов — в `pages`, действия — в отдельных фичах с публичным `index.ts`. Общие данные этапа, права и инвалидирование запросов — в `entities/stage`, когда появится повторное использование.
- Проверять идентификаторы до запроса. Состояние списков и выбранную дату дашборда хранить в URL.
- Показывать начальную загрузку, пустое состояние, ошибку с повтором и фоновое обновление. При ошибке сохранения сохранять ввод; конфликт версии требует обновления данных.
- Использовать серверные статусы и агрегаты. Деньги передавать в копейках, `null` отличать от нуля, отрицательный остаток показывать как переплату.
- После действий обновлять затронутые запросы этапа, чек-листа, материалов, выплат, объекта, списка мастера и дашборда.
- Проверять светлую и тёмную темы, клавиатурный фокус и ширины 390/768/1024/1440 px.
- Генерируемые файлы обновлять через кодогенерацию. Комментарии в коде писать по-русски.
- Серверные доработки не входят в эти планы. Недостающие данные API фиксировать как внешнюю зависимость, не заменять вымышленными данными.
