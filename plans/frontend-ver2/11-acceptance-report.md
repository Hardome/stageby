# Приёмка плана 11 — 17.10.2026

Фронтенд подключён к настоящему HTTP API на `localhost:3001` через Vite `localhost:3000`, PostgreSQL 18 и MinIO. Ответы API не подменялись. Для проверки повтора загрузки один PUT в MinIO намеренно прерван на сетевом уровне, затем ограничение снято. Для обхода большого числа экранов лимит запросов увеличен только в процессе локального API; `.env` и серверная модель не изменены.

Созданы отдельные тестовые пользователи `acceptance.1017.manager` и `acceptance.1017.foreman`, объекты №15 «Приёмка плана 11» и №16 «Приёмка 11 — границы». Существующие пользователи и объекты не редактировались. Тестовые данные оставлены для повторной проверки; пароли в репозиторий не включены.

## Сквозной сценарий через интерфейс

- Руководитель создал объект №15 с одним этапом, назначил мастера, задал ручные планы работ 1 000 ₽ и материалов 2 000 ₽. Начало этапа оставлено пустым, окончание — 25.10.2026. Создана начальная строка выплат на 1 000 ₽ без получателя и срока.
- Через форму добавлен PDF-счёт; файл прошёл upload-сессию, PUT и completion в MinIO. Сохранены независимые сумма счёта 2 000 ₽, факт оплаты 1 900 ₽ и доставка. Авторизованное скачивание PDF вернуло `200 application/pdf`.
- Мастер вошёл в свой кабинет, открыл этап по прямой ссылке, загрузил PNG. Перезагрузка сохранила фото; загрузка сама по себе не выполнила пункт. «Готово» перевело этап №34 на приёмку с прогрессом 100% и фактическим стартом 17.10.2026.
- В форме доработки конкурентное изменение этапа дало `409 version_conflict`. Замечание и выбор пункта сохранились; после обновления форма успешно отправлена. Новый срок по умолчанию — 19.10.2026.
- До повторной приёмки руководитель внёс 1 100 ₽. Этап остался на доработке, переплата отображена отдельно. Изменение текущего получателя строки не изменило получателя уже внесённого платежа.
- Мастер загрузил новый ракурс, повторно выполнил пункт. Руководитель принял работы, затем отдельно подтвердил «Выплачен». Этап получил `paid`, объект — `completed`; фактические даты сохранились.
- Через настоящий API к завершённому объекту добавлен дополнительный этап №35 с нулевыми планами. Объект снова стал активным. После реального фото, выполнения, приёмки и подтверждения выплаты объект вновь `completed`.

## Границы и ошибки

| Проверка | Результат |
| --- | --- |
| Независимые даты соседних этапов | У №36 задано только начало 20.10, у №37 — только окончание 18.10; соседние даты не перенесены |
| Нулевой и незаданный планы | При `0` создана строка на ноль, при `null` строк нет; итог проекта сохраняет `null` |
| Исключение и восстановление | №37 восстановлен с тем же ID и индивидуальным чек-листом; итог плана меняется с `0` обратно на `null` |
| История удалённых фото | После загрузки и удаления фото №36 исключение отклонено с `409 invalid_transition`; этап остаётся включённым |
| Атомарное сохранение | Устаревшая вложенная версия вернула `409 version_conflict`; имя клиента из той же формы не изменилось |
| Выплаченный этап | `null` и план 1 200 ₽ при факте 1 100 ₽ отклонены; 1 050 ₽ принят с сохранением `paid`, дат и исторического получателя |
| Истечение сессии | Удаление cookie имитирует потерю сессии; переход на вход сохраняет `returnTo=/stages/36`; вход того же пользователя возвращает к этапу |
| Отзыв назначения | После снятия мастера API возвращает `404`, страница показывает нейтральную заглушку без адреса объекта |
| Смена пользователя | Выход и вход другой ролью обновляют главную, заголовок, доступные действия и защищённые данные; регрессионные тесты проверяют очистку кэша и черновиков |
| Обрыв загрузки | PUT в MinIO прерван, показана ошибка; после перезагрузки очередь восстановлена из IndexedDB, повтор сохранил ровно одно фото; пункт до «Готово» не выполнен |
| Доработка после исправления | «Готово» заблокировано со старыми фото и доступно после нового фото, загруженного позднее решения руководителя |

Горизонтального переполнения нет. Эмуляция не считается проверкой физического Chrome или Safari.

Клавиатурный фокус виден, `:focus-visible` активен. Исправлен контраст блока завершения расчёта: используется существующий `Alert` с вариантом `success`; в тёмной теме текст `rgb(47, 111, 99)` на фоне `rgb(239, 250, 243)`. Проверены настоящие серверные состояния, переплата, замечания, просмотр после приёмки и недоступный этап.

Локальные скриншоты сохранены в игнорируемой папке `.playwright-mcp/`: `acceptance-11-stage-dark-390.png` (до исправления контраста), `acceptance-11-paid-dark-390.png` (после исправления). Это материалы текущей сессии, они не входят в Git.
