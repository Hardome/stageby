текущий код репозитория и [зафиксированные решения фазы 0](../docs/edited-ver2-baseline.md).
Это план работ, а не отметка выполненной реализации. Здесь `[ ]` означает предстоящую задачу.
Продуктовые решения R1–R18 приведены ниже и в заметке фазы 0. R1 и R12 согласованы и внесены в ТЗ:
план строится по планам этапов, факт — по внесённым выплатам и полностью оплаченным счетам.
По R13 согласованы наличные выплаты, ручной ввод администратором без документов и сохранение
получателя каждой выплаты при смене мастера этапа. По R2 на дашборде только таблица и индикаторы,
без задач; по R7 нехватку отдельно закрывает администратор. По R3 строка дашборда показывает
первый невыплаченный этап, по R4 объект завершён после выплаты всех включённых этапов,
по R5 старт следующего разрешён с предупреждением, если предшественник ещё не выполнен.
По R6 согласованы три цвета с приоритетом открытой нехватки и независимые подписи частичной
оплаты/доставки. По R8 выполнение только по «Готово», фото при выходе сохраняются. По R9 вход
остаётся по логину и паролю, телефон необязателен. R10 касается фронтенда и реализуется по отдельному
плану экранов; по R11 администратор подтверждает `paid` после приёмки
при остатке за работы ≤ 0, переплата допустима; по R14 даты этапов вводятся вручную внутри срока
проекта. По R15 счета добавляются только после создания в этапе; по R16 удаление фото через год
сохраняет выполнение/прогресс/статус, для нового выполнения и доработки нужно новое фото.
По R17 сервер использует время Екатеринбурга UTC+5 и горизонт дашборда сегодня…сегодня + 30 дней
включительно; адаптивность и браузерные проверки относятся к отдельным планам экранов. По R18 приёмка по подтверждению
администратора, без файла акта. Все R1–R18 согласованы; реализация ниже ещё предстоит.

## 1. Порядок и границы

Этот план охватывает только бэкенд: `api/`, исходные OpenAPI-контракты в `contracts/`,
модель данных, миграции, файловое хранилище, серверные бизнес-правила и тесты.
Фронтендом занимается другой разработчик по отдельным планам экранов: маршрутизация,
компоненты, формы, вёрстка, клиентские черновики и очереди загрузок, восстановление интерфейса,
адаптивность и браузерные проверки в этот план не входят. Общий `pnpm run codegen` может
обновлять generated-клиент в `web/` как производный артефакт контракта; это не задача реализации UI.
Готовность бэкенда определяется контрактами и проверками API и не зависит от готовности экранов.

Разработка ведётся поверх существующих auth/users/projects/stages/files/work-payments/materials/audit.
Сохраняются транзакции, права назначенного мастера, независимые факты оплаты и доставки,
`expectedVersion`, серверные денежные агрегаты и приватное файловое хранилище.

Уточнение пользователя от 04.10.2026: приложение ещё не запущено в production, сохранение
старых данных не требуется. При смене модели допускается сброс локальных данных; подготовка
старого набора, перенос данных и переходный период совместимости исключены из объёма.
Проверки чистой БД, бизнес-правил и аудита новых операций остаются обязательными.
В фазе 0 сброс данных не выполняется: проверки используют отдельные временные БД.

Порядок зависимостей:

1. Перенести согласованные правила в доменную документацию и проверить baseline.
2. Обновить модель, исходный OpenAPI и подготовить миграции.
3. Доработать материалы, справочник, чтение объектов/этапов и изменение сроков.
4. Подготовить API дашборда и недостающие операции.
5. Завершить серверные операции чек-листов/фото и правила переходов статусов.
6. Проверить сквозные сценарии через API и развёртывание бэкенда на чистой БД.

Приоритеты P0/P1 из ТЗ обозначают важность, но серверный цикл этапа зависит от чек-листа и фото.
Для работоспособного сценария «создание → выполнение → приёмка → выплата» они нужны в одном релизе.
Вторая итерация: отдельная роль приёмщика, инструмент, видео, фото материалов, внешние интеграции,
строительные нормы, карта размещения материалов. Их не включать в эту реализацию.
