# Stageby API

Серверная часть Stageby на Fastify и TypeScript. 
API использует OpenAPI как источник типов и схем валидации, Zod для проверки данных и Drizzle ORM для работы с PostgreSQL.

## Быстрый старт

Проще всего подготовить весь проект командой из корня репозитория:

```sh
pnpm run bootstrap
pnpm run dev
```

Для отдельного запуска API нужны Node.js 24.7+, pnpm 11+ и доступный PostgreSQL:

1. Скопируйте `.env.example` в `.env` и при необходимости измените настройки.
2. Выполните команды из каталога `api`:

```sh
pnpm install
pnpm run codegen
pnpm run db:migrate
pnpm run dev
```

По умолчанию API доступно по адресу [http://127.0.0.1:3001](http://127.0.0.1:3001), интерактивная документация — по адресу [http://127.0.0.1:3001/documentation](http://127.0.0.1:3001/documentation).

## Переменные окружения

| Переменная | Значение по умолчанию в `.env.example` | Назначение |
| --- | --- | --- |
| `NODE_ENV` | `development` | Режим работы: `development`, `test` или `production` |
| `HOST` | `127.0.0.1` | Адрес, на котором слушает сервер |
| `PORT` | `3001` | Порт HTTP-сервера |
| `LOG_LEVEL` | `debug` | Уровень логирования |
| `DATABASE_URL` | `postgresql://postgres:postgres@localhost:5432/stageby` | Строка подключения к PostgreSQL |
| `CORS_ORIGIN` | `http://localhost:3000` | Разрешённые источники CORS через запятую |
| `API_PUBLIC_ORIGIN` | `http://127.0.0.1:3001` | Доверенный публичный origin API и Swagger UI, без пути и завершающего `/` |
| `TRUST_PROXY` | пусто | IP или CIDR доверенных reverse proxy через запятую; по умолчанию forwarded-заголовки не используются |
| `RATE_LIMIT_MAX` | `100` | Максимум запросов за заданное окно |
| `RATE_LIMIT_TIME_WINDOW` | `1 minute` | Окно ограничения частоты запросов |
| `LOGIN_RATE_LIMIT_MAX` | `5` | Максимум попыток входа отдельно для IP и логина за заданное окно |
| `LOGIN_RATE_LIMIT_TIME_WINDOW` | `1 minute` | Окно ограничения попыток входа |
| `SESSION_TTL_HOURS` | `12` | Срок действия сессии в часах, от 1 до 12 |
| `SESSION_CLEANUP_INTERVAL_SECONDS` | `3600` | Интервал удаления истёкших сессий; одна попытка удаляет до 1000 записей |

## Команды

| Команда | Назначение |
| --- | --- |
| `pnpm run admin:create-first-manager` | Создать первого руководителя в пустой базе |
| `pnpm run dev` | Запустить сервер с перезапуском при изменениях |
| `pnpm run build` | Обновить сгенерированный код и собрать проект в `dist` |
| `pnpm run start` | Запустить собранный сервер |
| `pnpm run codegen` | Сгенерировать типы и схемы из OpenAPI-контракта |
| `pnpm run typecheck` | Проверить типы TypeScript |
| `pnpm run lint` | Запустить Biome с автоматическим исправлением, cspell, проверку типов и Knip |
| `pnpm run lint:knip` | Найти неиспользуемые файлы, экспорты и зависимости |
| `pnpm run test` | Однократно запустить тесты |
| `pnpm run test:watch` | Запустить тесты в режиме наблюдения |
| `pnpm run db:generate` | Создать SQL-миграцию по изменениям схемы |
| `pnpm run db:migrate` | Применить ещё не выполненные миграции |
| `pnpm run db:studio` | Открыть Drizzle Studio |

Для проверки Knip используйте `pnpm run lint:knip`: команда передаёт `tsconfig.build.json`, чтобы корректно сопоставлять импорты из `dist` с исходниками в `src`.

Интеграционным тестам требуется доступный PostgreSQL из `DATABASE_URL`. Перед запуском Vitest создаёт отдельную временную базу, применяет к ней миграции и удаляет её после завершения, поэтому данные и sequence основной базы не изменяются. Пользователь подключения должен иметь права на создание и удаление баз. Локальный PostgreSQL можно запустить из корня репозитория командой `pnpm run db:up`.

## Структура

```text
api/
├── src/
│   ├── config/         # разбор и проверка конфигурации
│   ├── db/
│   │   ├── migrations/ # SQL-миграции Drizzle
│   │   └── schema/     # схема базы данных
│   ├── generated/      # код, сгенерированный из OpenAPI
│   ├── modules/        # бизнес-модули и HTTP-маршруты
│   ├── plugins/        # плагины Fastify
│   ├── app.ts          # сборка приложения
│   └── server.ts       # точка запуска сервера
└── test/               # общая инфраструктура тестов
```

Правила структуры модулей, импортов и репозиториев описаны в [руководстве по API-модулям](../docs/api-modules-guidelines.md). За рабочий пример можно взять модуль `users`.

## Контракт и генерация кода

Источник истины — [`contracts/references/stageby/stageby.yaml`](../contracts/references/stageby/stageby.yaml), объединяющий файлы сущностей. После изменения исходников выполните из корня Stageby `pnpm --dir contracts run generate`, чтобы обновить собранный `contracts/openapi.yaml`. Команда `pnpm run codegen` читает этот файл, обновляет `src/generated` и затем проверяет типы. Сгенерированные файлы вручную не редактируются. Реализованы серверные модули авторизации, пользователей и проектов; остальные предметные маршруты пока описаны контрактом.

Если контракт используется веб-приложением, после изменения также выполните из корня:

```sh
pnpm --dir web run codegen
```

## База данных и миграции

Схемы таблиц находятся в `src/db/schema`, SQL-миграции — в `src/db/migrations`. После изменения схемы выполните:

```sh
pnpm run db:generate
pnpm run db:migrate
```

`db:generate` создаёт миграцию, но не изменяет базу. `db:migrate` применяет только ещё не выполненные миграции и записывает их в журнал Drizzle. Подробности и порядок отката описаны в [руководстве по базе данных](../docs/database-guidelines.md).

## Первый руководитель

После применения миграций запустите административную команду:

```sh
pnpm run admin:create-first-manager
```

Команда интерактивно запросит логин, ФИО и пароль. Пароль при вводе не отображается. `DATABASE_URL` читается из окружения или `.env`. Для автоматического развёртывания интерактивный ввод можно заменить переменными `FIRST_MANAGER_LOGIN`, `FIRST_MANAGER_PASSWORD` и `FIRST_MANAGER_FULL_NAME`; необходимо задать все три.

Команда не выводит пароль и доступна только локально — HTTP-маршрута для неё нет. Она создаёт активного пользователя с ролью `manager`, только если таблица `users` пуста. При повторном или одновременном запуске существующие записи не меняются, а команда сообщает, что база уже инициализирована.

## Авторизация в браузере

<!-- cspell:ignore Referer -->

`POST /auth/login` устанавливает cookie `stageby_session`. Она недоступна JavaScript (`HttpOnly`), передаётся для всех путей (`Path=/`), использует `SameSite=Lax` и получает флаг `Secure` в production. Клиентские запросы должны использовать `credentials: include`; разрешённые CORS-источники задаются через `CORS_ORIGIN`. Секрет сессии не возвращается в JSON и не хранится в `localStorage` или `sessionStorage`.

Все запросы, кроме `GET`, `HEAD` и `OPTIONS`, должны передавать доверенный `Origin` или, если он отсутствует, `Referer`. Источник сверяется с `CORS_ORIGIN` и `API_PUBLIC_ORIGIN`, включая протокол и порт; заголовок `Host` не предоставляет разрешение. Источник `null`, некорректный или отсутствующий источник возвращает `403`. Это относится и к входу, и к запросам из командной строки: например, передавайте `Origin` из настроенного списка. Все ответы API, включая ошибки, получают `Cache-Control: no-store`.

В production задайте `API_PUBLIC_ORIGIN` явно, если используете Swagger UI на адресе API. Автоматический локальный адрес применяется только вне production. За reverse proxy задавайте в `TRUST_PROXY` только адреса реальных доверенных прокси, чтобы ограничения по IP различали клиентов. Ограничения запросов хранятся в памяти процесса; перед запуском нескольких экземпляров API потребуется общее хранилище счётчиков.

Выдача сессии повторно проверяет пользователя под блокировкой в транзакции. Параллельное изменение пароля, роли или активности не позволяет выдать сессию по устаревшим данным. После успешного входа устаревшие параметры Argon2id обновляются в той же транзакции без отзыва других сессий. Очистка истёкших сессий не выполняется параллельно внутри процесса, записывает ошибки в журнал и завершается до закрытия подключения к БД.
